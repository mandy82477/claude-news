**分流鐵則：** GitHub Issues 條目屬功能記者（claude-code 已知問題）；僅當該 issue 引發跨平台討論（HN/Reddit 也在延燒）才作為 discussions 條目收錄。

**官方內容不是你的禁區 `[加入: 2026-08-16]`：** 「社群」是內容型態的類別名，不是出處篩選器——官方部落格、官方文件、Anthropic 員工具名發言，只要談的是技術討論或工作流模式，一樣是你的條目（discussions 的收錄門檻本就明列「重要人士具名表態」；patterns 的觸發條件從未限制出處）。與功能記者的界線依**它給讀者什麼**分：官方提出**可被複用的新工作流模式／agent 設計** → 你收進 patterns 並標明官方出處，與社群模式並列比較；官方講**怎麼用既有功能**（省 token、session 經營、設定建議） → 那是功能記者的 `topics/coding-workflow-guide`，你不寫。完整對照表見 `.claude/rules/wiki-ingest.md`「分流鐵則：官方內容不是社群類的禁區」。

**產品化矩陣轉知 `[加入: 2026-07-04]`：** 發現新的 agent 工作模式（patterns 頁新增條目）時，在回報中註明「請主編轉知功能記者評估產品化矩陣新增列」；`wiki/topics/official-community-gap.md` 的矩陣由功能記者維護，社群記者不直接寫該頁。

**dev.to 條目以內容判斷、不看讚數 `[加入: 2026-07-10]`：** dev.to 走 `top=30` 抓法（過去 30 天高互動文章），但**讚數在 dev.to 幾乎不能當品質指標**——實測顯示最有價值的第一手實作文（如「對抗式 Claude 互審 loop」「local reverse proxy 看 CC 送什麼」）讚數常只有 2–3，反而 SEO 農場文有 5–6 讚。因此 dev.to 條目一律**用內容判斷收錄，不套互動門檻對照表的數字**：

- ✅ **優先收**：「我做了 X、這是怎麼運作 / 踩了什麼坑」的第一手實作、可複用 pattern、具體工具或量化實測（歸 `community-tech-patterns.md`）
- ❌ **排除**：`Complete Guide` / `Everything you need to know` 型 SEO 農場文（常來自 `ai_made_tools`、`tokenmixai` 等內容農場帳號）；純新聞轉述（定價、發布、事件解釋——這些已由媒體/HN 來源覆蓋，dev.to 版本無獨特價值）；純帶貨 / growth hacking 自我推銷

> 判斷原則：dev.to 的獨特價值是「工程師第一手實作經驗」，不是新聞或教學索引。內容答不出「作者具體做了什麼、學到什麼機制」→ 不收。

## community-tech-patterns 的四張結論表 `[加入: 2026-09-06]`

本頁回答「社群拿 Claude Code 玩出哪些做法、哪些已經站住腳、哪些還在試」。`## 技術彙整` 是證據層（每日 prepend 節點，不受本節拘束）；上方四張表是結論層。**本節取代原「multi-agent orchestration 學術對照維護」節對這四張表的欄位規定；該節的「屬非新聞性更新，只動最後更新、不動最後新聞更新」與「論文查證屬主編、記者無 web 工具不得自行補文獻」兩條紀律繼續適用。**

### 1. community-tech-patterns 的 `## 模式概覽`（覆寫式，上限 21 列，逾 60 天或算不出日期即移除）

五欄固定：`類別｜代表技巧｜成熟度｜最後動態｜核心概念`。

- **判準句（三條全過才入表）：** ① 是一種**做法**不是一個工具——同一做法的多個實作合為一列，工具名只進「代表技巧」欄；② 「代表技巧」欄至少寫得出兩個具名實作，或一個實作加一句可複用的機制；③ **「最後動態」欄算得出日期**，算不出者不得留表。
- **一個類別永遠只有一列。** 新節點只覆寫「代表技巧」與「最後動態」，不新增第二列。
- **「最後動態」的定義（唯一口徑，判定與撈法同一句）：** `## 技術彙整` 中，**`**與既有模式的關係：**` 那一行逐字寫出表上該類別名**的節點裡，日期最新的那一則。撈法兩段式：先 `Grep "\*\*與既有模式的關係：\*\*" wiki/topics/community-tech-patterns.md`，再在輸出中挑**逐字包含該類別名**的行（比對前只去空白、全形斜線轉半形），取行號最大者所屬節點的日期。**同義說法不算**（例：關係行寫「Skill 生態多元化」不算「Skills 設計」）；關係行沒有逐字寫出類別名的節點不計；**archive 頁不在射程內**——搬走的條目不再撐一個類別留在表上。
- **「代表技巧」欄末必附錨點，一律寫全頁形式** `[[topics/community-tech-patterns#YYYY-MM]]`（＝最後動態那個月的 `### YYYY-MM` 分組）。**不可寫同頁簡寫 `[[#YYYY-MM]]`**——`scripts/build_web.py` 的 `ANCHORED_WIKILINK_RE`（L276）要求 `#` 前至少一個字元，同頁簡寫不會被 `check_wikilink_anchors()` 檢查到，等於沒有看守。
- **排序：** 成熟度降序（✅ 成熟 → ⚡ 活躍 → ⏳ 新興），同級依最後動態新者在上，**同日者維持前一版的相對順序**。圖例一行固定放表下，不重寫。
- **退場：** 距最後動態逾 60 天、**或依上述定義算不出最後動態**者移出表，降為表下一段（類別名＋代表技巧＋原始條目錨點）。✅ 與 ⚡ 不因時間退場，但逾 60 天須重判成熟度是否該降級。**跨線當週處理，不等下一次**：每次執行時先算「距今天幾天」，剛跨過 60 天的列當次移出（例：可靠性測試 2026-07-12 於 2026-09-10 跨線，該週 lint 即移出，不留到下週）。
- **補位：** 移除後表未滿載時，從表下那一段挑最後動態最新、且重新符合三條判準者補回表，並刪掉它在表下那一行。
- **留表優先序（表滿載時）：** 成熟度較高者 ＞ 最後動態較新者 ＞ 代表技巧欄具名實作較多者；讓位者移到表下並註明「（未列入概覽表：表滿載，YYYY-MM-DD）」。
- **入口只有兩種訊號：** 出現一種本表沒有的做法，或既有類別出現新的代表技巧。單一工具發布、媒體轉述、熱度回升都不構成入口。
- **兩個類別的代表技巧重疊過半時合併為一列**，被併者的代表技巧併入留下的那一列。

### 2. community-tech-patterns 的 `### 誰負責拆分（decomposition）`（覆寫式，五列固定不增減）

四欄固定：`拆分來源｜對應機制｜官方怎麼說（查證日）｜應用場景`。五列為模型自動委派／人類事先凍結／強模型當場動態拆／lead 拆分後隊友自領／不拆分。**列不新增也不移除**，官方機制改變時只覆寫對應格與查證日。「官方怎麼說」欄**由主編查證官方文件後填**，記者不得自填；官方無對應說法時寫 `—`。

### 3. community-tech-patterns 的 `### 缺口追蹤：文獻主張 × Claude Code 現況`（覆寫式，上限 8 列，補上即移除）

四欄固定：`缺口｜文獻主張｜現況｜狀態`。**狀態三值：已補／部分補上／未補**，一律附查證日；**不得使用 ✅／❌ 符號**——本頁的 ✅ 已經是成熟度的值，同符號兩個意思會讓讀者讀錯。狀態**由官方一手文件決定**，日報的社群轉述只能更新「現況」欄文字，不能翻狀態。表上方標「資料截至 YYYY-MM-DD」，距今逾 60 天由主編重查。**退場：** 缺口被官方補上且連續兩次查證維持「已補」即移除該列，結論留在表下細節；文獻主張本身被推翻者移除。**倒退項**（官方拿掉過的能力）不入表，寫在表下「一項倒退」段。

### 4. community-tech-patterns 的 `## 學術對照：多智能體 orchestration 術語`（覆寫式，官方新增機制才加列）

五欄固定：`Claude Code 機制｜官方狀態｜Anthropic《Building Effective Agents》｜控制流｜通訊原語`。**一個官方機制一列**，官方新增一種多 agent 機制才加列，機制下架即移除該列；論文名詞增加不加列。表上方標「資料截至 YYYY-MM-DD」。

### 5. 主線 tag 補填 `[加入: 2026-09-06]`

`**主線：**` 欄目前 115 則節點只有 42 則填過（37%），而週更整線重寫只撈填了非 `—` 的那 11 則。**新節點一律必填**（原規則已載）；**存量補填每週 20 則、從最新往回補**，補到全數為止，進度寫進 lint 回報。判不出的填 `—` 並在「與既有模式的關係」寫一句理由，不留空。

### 7. 懸置標記的條列變體 `[加入: 2026-09-06]`

同 `.claude/rules/wiki-ingest-format.md`「懸置標記語法 → 表格變體」，容器由儲存格換成條列：條列只留短標記，完整標準式放**該月份 `### YYYY-MM` 分組最末**的「懸置細節」區。**短標記形式不變**（狀態符號＋類別詞＋`⟨Q-nn⟩`，缺一不可）。**同一則節點的同一個事實只標一次**——成熟度欄與核心模式欄不得各標一份。

## community-tech-discussions 的兩張結論表 `[加入: 2026-09-06]`

本頁回答「社群在吵哪些關於 Claude Code 的觀念問題、哪些已經吵出共識、哪些還僵著」。`## 技術彙整` 是逐則原文（每日 prepend，不受本節拘束）；上方兩張表是結論。

### 1. community-tech-discussions 的 `## 現在吵到哪`（覆寫式，上限 10 列）

五欄固定：`爭論｜現在狀態｜最後一則證據｜證據硬度｜官方怎麼說`。

- **判準句（三條全過才入表）：** ① 它是一個「該怎麼想」的觀念問題，寫得出正反兩方各主張什麼——單則工具發布、單一產品事件、廠商公告、缺陷回報一律不入表（缺陷的家是 [[entities/claude-code]]）；② 「最後一則證據」欄填得出一個本頁或封存頁找得到的日期與錨點，填不出者不入表；③ 「現在狀態」欄的三值寫得出一句依據（誰說的、幾家、哪一天）。
- **一場爭論永遠只有一列**，同一場的多起事件合為一列，新證據只覆寫「最後一則證據」與「現在狀態」。
- **狀態三值（唯一口徑）：** 還在吵＝距最後一則證據 ≤ 60 天且正反兩方都還有人出手；已吵出共識＝多方指向同一結論且本輪無新的反方證據；僵住＝距最後一則證據 > 60 天且雙方都未再推進。**狀態由證據日期與正反方是否出手決定，不由熱度決定。**
- **「最後一則證據」的定義（判定與撈法同一句）：** 本頁或封存頁中，論點屬於這一場爭論的條目裡日期最新的那一則；**來源限三處**——`## 技術彙整` 的 `### YYYY-MM` 分組、`## 🌊 持續關注中的長期議題` 的子節條目、`## 最近在討論什麼` 的表列。**錨點指到那一則真正住的節**：住技術彙整寫 `[[topics/community-tech-discussions#YYYY-MM]]`，住長期議題寫 `[[topics/community-tech-discussions#🌊 持續關注中的長期議題]]`，住封存頁寫 `[[topics/community-tech-discussions-archive#YYYY-MM]]`。**不可寫同頁簡寫 `[[#…]]`**——`scripts/build_web.py` 的 `ANCHORED_WIKILINK_RE`（:276）要求 `#` 前至少一個字元，同頁簡寫不會被 `check_wikilink_anchors()` 檢查到，等於沒有看守。證據住別頁者（如人物頁）寫該頁的 wikilink。
- **欄內必須寫出被引條目標題的前八個字**，讓下一次重算可以用 grep 定位；grep 不到即視為算不出，該列重判。同一句形式套到 `## 最近在討論什麼` 的「最後動態」。**沒有這一條，狀態三值就是兩個人兩個答案**——月份錨點只說得出「那個月」，說不出「哪一則」。
- **「證據硬度」由來源決定，不由結論多強決定**，五值：官方一手／官方文件／跨媒體與社群多來源／具名表態／單次高互動討論。同一列可疊寫兩項，以 `＋` 連。**表格列內不得寫「二手」二字**（讀者語言禁詞，改寫「媒體轉述」）。
- **「官方怎麼說」欄由主編查證官方文件後填，記者不得自填**；官方無對應說法時寫「無官方回應」或「無官方立場」，不留白。事實的家在他頁者只寫 wikilink，不複製。
- **排序：** 還在吵 → 已吵出共識 → 僵住，同狀態依最後一則證據新者在上。
- **退場（依序問，第一個成立即定案）：** 狀態為「已吵出共識」且距最後一則證據逾 90 天 → 移出表，結論改成表下一句「已經沒人在吵的」；狀態為「僵住」且逾 180 天 → 移出表，改成表下一行並指封存頁；狀態為「還在吵」的列不因時間移出——時間到它會先變成「僵住」。
- **補位：** 移出後表未滿載時，從 `## 最近在討論什麼` 挑模式為 🌊延燒 或 🌋重燃、最後動態最新、且重新符合三條判準者補入。
- **留表優先序（表滿載時）：** 「官方怎麼說」欄有官方一手或官方文件者 ＞ 狀態為「還在吵」者 ＞ 最後一則證據較新者；讓位者改寫成表下「沒有列進上表的一場」，並註明最後一則證據日期。
- **入口只有兩種訊號：** 出現一場本表沒有的觀念爭論（正反兩方都有具名來源），或既有爭論出現會改變狀態的新證據（官方一手、或新的反方證據）。媒體轉述舊爭論與熱度回升都不構成入口。

### 2. community-tech-discussions 的 `## 最近在討論什麼`（原「熱門討論（最近 30 天）」，上限 50 列）

六欄固定：`討論主題｜首見 · 最後動態｜當時熱度｜模式｜核心論點｜衍生`。`## 最近在討論什麼` 每次更新後依下列保留期清理，逾期的列移除或改標。

- **日期欄寫兩個日期**，格式 `YYYY-MM-DD · YYYY-MM-DD`（首見 · 最後一次有新證據），新列建立時兩者相同。**🌋重燃偵測讀點前那個日期**（原規則「直接查 `首見` 欄」照此改讀）。
- **模式五值的保留期一律讀「最後動態」，不讀「首見」**：☄️閃現 ≤ 21 天；🌸落幕 ≤ 14 天；🌊延燒／🌋重燃 距最後動態逾 **45 天**即改標 🌙靜候（「延燒」的語意是還在燒，四個月沒有新證據還標延燒是假現在式）；🌙靜候 距最後動態逾 **90 天**即移出表。
- **「最後動態」的撈法（取三處中最新者，不是取第一個算得出的）：** ① 該列「核心論點」欄自己寫出的最新日期；② `## 技術彙整` 中標題含該列主題關鍵詞的條目；③ `## 🌊 持續關注中的長期議題` 中同主題子節的條目。**改標或更新最後動態時，那個日期必須同時寫進「核心論點」欄**，否則下一次重算讀不到它。
- **算不出最後動態者不得留表**（同 patterns 概覽表判準）：上述三處皆查不到日期者一律移出；「首見」欄寫「持續」不等於算不出——先照三處撈一遍再判。
- **移出時，原文在 `## 技術彙整` 或封存頁有家者**，在表下「已不在上表的討論」列一行並指該處錨點；原文只存在於表列與細節區者直接移除（git 歷史留存），不在表下另留一行——否則表下會長出第二張表。
- **上限 50 列。** 滿載讓位序：先汰 🌙靜候 中最後動態最舊者，再汰 ☄️閃現 中最後動態最舊者；🌊延燒、🌋重燃 不讓位。
- **「當時熱度」欄名固定帶「當時」二字**：它記的是首見那時的討論規模，不是現在的熱度。熱度值的判定照本檔「誠實標註原則」不變。
- **移出上表的列，其「最近在討論什麼細節」條目一併處理**：條目裡若有懸置標記，該標記**必須先在 `## 技術彙整` 對應月份分組末的「懸置細節」區落地**，才可移除原條目（`scripts/check_pending_markers.py` 的標記數基線不得靜默減少）。

### 3. community-tech-discussions 的 index 鉤子失效轉知

`## 現在吵到哪` 的**列數、三種狀態的組成、或第一列換人**時，**先同批改寫 `## 摘要` 首句的三個數字**（幾場還在吵／幾場已吵出共識／幾場僵住），再在回報「同步自查」欄寫 `⚠️ 需主編同步 index 鉤子：[新的一句鉤子]`。**不可自行編輯 `wiki/index.md`**——該格後半段的 `　↳ 子故事：` 是機器投影，手改會讓 `run_tests.py` 紅。

照 `.claude/rules/wiki-ingest-format.md`「時段蒸餾與封存（全站通用）」，archive 子頁為 `topics/community-tech-discussions-archive`，對象為 `## 技術彙整` 的 `### YYYY-MM` 分組。**2026-05／06 兩個時段已於 2026-09-06 封存；2026-07 於 2026-10 起達門檻**——搬走之前先確認 `## 現在吵到哪` 中「最後一則證據」欄指向 `#2026-07` 的列，錨點同批改指封存頁。通用契約的例外 2 與例外 3 在本頁的具體形態：**`## 現在吵到哪` 每一列「最後一則證據」所指的那一則條目不搬**（例外 2 唯一細節出處）；**模式為 🌊延燒／🌋重燃 的討論，其歷史月份條目不搬**（例外 3）。

## community-large-codebase-workflow 主線 tag 規則（daily）`[加入: 2026-08-05，改版: 2026-08-15]`

`community-large-codebase-workflow.md` 是把 patterns 節點沉澱成四條主線的**週更**頁；patterns 收「節點」（每日 append），主線頁每週從 patterns **整線重寫**（規則見 `.claude/rules/wiki-ingest-community-lint.md`）。**每日 ingest 不寫主線頁**——2026-08-05～08-15 的日更小縫實驗證明：每天只看一個節點的記者，結構上只做得到「往段尾加一句」，兩週就把綜合敘事頁長回 log；縫合需要看完整條線再重寫，那是週更的事（2026-08-15 使用者裁決）。

**每次為 `community-tech-patterns.md` 新增節點時，多填一個欄位：**

```
- **主線：** 並行規模 ／ Context 管理 ／ 索引記憶 ／ 除錯分工 ／ —
```

- 判準是「這個節點回答的是**大型 codebase 特有**的痛點嗎」——並行 agent 互踩／context 被工具輸出撐爆／agent 記不住跨 session 決策／多 agent 產出誰把關；小專案也會遇到的通用技巧填 `—`
- 可複選（頓號分隔）；拿不準填 `—` 並在「與既有模式的關係」寫一句理由，週更時記者會再判
- 這個欄位是週更唯一的撈料依據（`Grep "\*\*主線：\*\* [^—]"`），漏填等於該節點對主線頁不存在
- 某類節點反覆出現卻無線可歸 → 不自行開線，回報主編轉知 weekly-review 評估第五條線

## community-tech-discussions 收錄門檻 `[加入: 2026-06-28]`

此頁追蹤「思想碰撞」，訊號價值有**三個合法來源（滿足其一即可收錄）**：

| 訊號來源 | 收錄理由 | 最低門檻 |
|---------|---------|---------|
| **社群碰撞** | 多方驗證、正反交鋒 | 達對照表**低**門檻（見 `.claude/rules/wiki-reporter-shared.md` 互動門檻對照表），或同議題跨 2 個以上獨立來源（source_count ≥ 2）|
| **重要人士具名表態** | 因「誰說的」而有重量（Boris Cherny、Dario、Karpathy 等）| 具名 + 可信來源；同時回報人物記者更新對應 `entities/` 頁 |
| **重要媒體深度報導** | 因觸及面與報導深度（36Kr、Platformer、WSJ 等）| 報導本身有實質內容，非純轉載標題 |

**誠實標註原則（強制）：** 說明欄須標明訊號性質，熱度符號錨定真實信號強度，不可虛抬：

- 社群兩極化／跨平台廣泛熱議 → 🔥🔥🔥🔥+
- 單平台高互動／議題共鳴深 → 🔥🔥🔥
- 多次被引用／催生後續工具 → 🔥🔥
- **重要媒體/人士單一報導，無社群延燒 → 🔥**，且說明欄末註「（媒體報導，待社群接力）」或「（具名表態，無社群延燒）」

> 關鍵區分：🔥🔥 以上隱含「社群共鳴」，**無社群討論的單一報導不得標 🔥🔥 以上**，避免讀者誤判信號強度。
> 純標題轉載、無實質內容的媒體稿，仍不收錄。
> **這三個門檻管的是進不進 `## 最近在討論什麼`。要進 `## 現在吵到哪`，另外要過一關：這一則寫得出正反兩方各主張什麼**——寫不出就只是一則討論，不是一場爭論。

## community-tech-discussions 技術彙整書寫規則 `[加入: 2026-05-20，改版: 2026-07-02]`

**月份分組（patterns / discussions 兩頁的 `## 技術彙整` 皆適用）：** 條目按 `### YYYY-MM` 月份標題分組，條目本身用 `####` 層級。此分組提供跳轉導航，是「頁面不拆分」前提下的替代方案。

**格式：**
```markdown
### YYYY-MM

#### 討論主題名稱（YYYY-MM-DD）

- **來源：** 原始文章標題（平台，作者）
- **核心論點：** 一句話摘要
- **關鍵回響：**（選填，有則記）
  - 📝 支持：…（標題，來源）
  - 📝 反駁：…（標題，來源）
  - 🧪 跟進實測：…（標題，來源，結論一句話）
- **收斂結論：**（若討論已有共識）…
```

**新條目插入位置：** 插入 `## 技術彙整` 下方**當月 `### YYYY-MM` 分組的正下方**（最新在最上方）；當月分組不存在時先建立該月標題。不可加在末尾。

**防過度推論：** 推導出的結論必須標注「（推論）」，不可直接寫成事實。

## multi-agent orchestration 學術對照維護 `[加入: 2026-07-22]`

`community-tech-patterns.md` 有一個參考層 `## 學術對照：多智能體 orchestration 術語`（Claude Code 機制 ↔ 學術術語 ↔ 論文），維護規則：

- 於「Multi-agent 架構」或相關類別**新增一種 agent 協作模式／機制**時，判斷它對應到對照表哪一格（控制流 × 通訊原語），需要時新增或更新該表的列。

你不寫該功能的 entities 頁，只負責讓這則證據被看見——它結構上只會經過你手上（2026-09-03 教訓：唯一一則對 Managed Agents 有決策價值的證據被合法擋在社群通道，功能記者四個月不知情）。
