## 更新規則

**模型頁基本欄位：** 每次更新必須同步「最後更新」日期。若狀態改變（如 `beta` → `active`），標記回報讓主編同步 `wiki/index.md`。

**評測數據：** 優先記錄官方或三方確認來源，補注測試日期。若有相互矛盾的評測結果，保留兩者並標注來源。

**版本號：** 模型版本號視為元資訊（`entities/` 標頭），不另建頁面。若版本迭代有重大能力差異，加入 `## 歷史記錄` 條目。

**定價歸屬：** 模型本身（能力、評測）進模型頁；定價細節進 `wiki/entities/pricing.md`（**商業記者主責**，模型記者不直接維護該頁）。同一事件有兩面向時，模型記者記能力面、商業記者記定價面，互相加 wikilink。

**選型對照同步 `[加入: 2026-07-02，補強: 2026-07-12]`：** `wiki/topics/model-comparison.md` 是「我該用哪個模型」的單一入口。任一模型發布/下線/狀態/定價/Claude Code 預設變更時，除更新該模型頁外，**必須同步更新對照頁的快速選型表與情境推薦**；深度細節仍留在各模型頁，對照頁只放一行式結論。此項納入回報的「同步自查」欄。

**日期類事實尤其容易漏（2026-07-08→07-12 的教訓）：** 免費期限、促銷截止日這類「會員疊延長」的日期，往往同時寫在模型頁的「現況」段落＋模型頁自己的子標題/內文＋`model-comparison.md` 快速選型表三處以上。單純判斷「陣容/定位未變」不足以跳過同步——**只要有舊日期字串（如 7/7、7/12）殘留在任何一處描述「當前」或「即將」的句子裡，就必須視為需要同步**，不能只更新歷史記錄新條目就結案。修改前對舊日期字串在該模型頁全文 + `model-comparison.md` 各 grep 一次。

## model-comparison 選型品質審核 `[加入: 2026-07-26]`

`wiki/topics/model-comparison.md` 是「我該用哪個模型」的單一入口，**它的成敗不在資訊齊不齊，在讀者能不能據以決定**。2026-07-26 深度 review 判定該頁決策層為全頁品質最低處（三個模型的「最適合」全部命中 agentic 而無分界、「不適合」16 格中僅 2 格可據以決策、決策層零來源歸因）。以下為此後的硬規則。

### A. 每條「適合／不適合」必須帶可驗證分界

**禁止同義反覆**——「適合複雜任務」「不適合簡單任務」「偏好其互動個性者」這類寫法一律不合格，因為它沒告訴讀者怎麼判斷自己的任務算不算「複雜」。

分界至少要落在下列可驗證維度之一，並寫成讀者能自我對號的形式：

| 維度 | 可用的寫法範例 |
|------|--------------|
| 任務時長 / 步數 | 「單次 < 30 分鐘」「數小時自主執行」「跨多天」 |
| 改動規模 | 「改動 < 5 檔」「跨 40 檔以上的 refactor」 |
| Context 需求 | 實際 token 量級，不是「很長」 |
| 延遲要求 | 「即時互動」vs「可離線批次」 |
| 成本敏感度 | 具體倍數或預算門檻 |
| 是否需 tool use / 工具密集度 | — |
| 失敗代價 | 「可人工複核」vs「錯了難回收」 |

**換模型不是唯一旋鈕**：官方明載「調 effort 通常比換模型更有效」（`choosing-a-model`）。凡建議升級模型處，先確認是否該建議調 effort。

### B. 不可用讀者取不到的模型當唯一淘汰基準

Mythos 5（僅限授權機構）這類非公開陣容的模型，只能作為補充對照。**若某模型因「不及某受限模型」而被判不適合，必須同時回答「在公開陣容中該選誰」**——否則讀者只知道「都不夠好」，會退回更差的選項。

### C. 社群效能討論一律留數字 `[使用者指示: 2026-07-26]`

社群出現任何**模型效能面的量化討論**（benchmark 分數、成本倍數、token 消耗、延遲、成功率、context 實測上限、勝率），**數字必須進頁面**，不可壓縮成「表現不錯」「有落差」這類定性描述——數字才是讀者用來決策的東西。

每筆附三項：**樣本條件**（測了什麼、幾則、什麼任務）、**來源與日期**、**訊號強度**（官方基準 / 多來源實測 / 單一社群回報）。同議題出現相反數字時**並陳，不擇一**；查不到具體數字時標「待查證」，不可推算或以形容詞代替。

### D. 決策層的嚴謹度不得低於證據層

快速選型表與情境推薦的每一條建議都要能回答「依據是什麼」（官方文件 / 官方基準 / 社群實測 + 日期）。**不可出現「證據區每列都有來源日期與訊號強度、決策區整片沒有歸因」的倒置**。

### E. 陣容換代時同步骨架

新模型發布取代既有階層時，benchmark 對照表的**欄位骨架**要跟著換；一時無新模型數據，就在表上方整表標「本表為 <舊陣容> 對照，<新模型> 數據待補」，**不可把新模型硬塞成一個列**（讀者無法橫向比）。同時 grep 全頁確認舊模型的「獨佔優勢」敘述是否仍成立（2026-07-26 教訓：Opus 4.8 的「Fast Mode 省時場景」在 Opus 5 也支援 fast mode 後已不成立，卻讓讀者有理由留在已被取代的模型）。

### F. 3 跳自檢（每次更新此頁後執行）

取 2 個真實任務描述（例如「跨 40 檔的 refactor，估 2 小時」「高頻批量分類，延遲敏感」），從 `wiki/index.md` → 本頁 → 對應區塊，**3 跳內是否得到單一明確建議**。

- 落在兩列之間、或多個模型同時命中而無從取捨 → **不合格**，補列或改判準
- 結果寫入回報的「同步自查」欄

### G. 儲存格短語化：表格放結論，細節下沉 `[加入: 2026-08-04]`

C 條「數字必須進頁面」與 D 條「決策層必須歸因」的正確落點是**表格下方的細節區，不是儲存格裡**。2026-08-04 讀者回報本頁不可讀——查證過程、官方原文比對、多來源歧異全被塞進儲存格，最寬一列 996 字元、單格 700+ 字元，網站上多欄表格直接爆版。

- **儲存格 ≤ 120 字元**：放結論短語＋關鍵數字；超過就把細節下沉到該表格正下方的細節區（先例：快速選型表的「選型細節」區，07-26 建立）
- 細節條目開頭用表內關鍵詞錨定，讀者從表列能對上細節
- 下沉是搬位置不是刪除——C/D 條要求的數字與歸因一個都不能少
- **純引用來源格豁免**（標題＋URL＋日期）：markdown 連結的 URL 吃字元數但渲染後只顯示連結文字，不算散文塞格
- 每次更新本頁後自查（量測前先剝掉連結 URL，只算渲染可見文字）：

  ```
  python -c "import re;[print(n,len(c)) for n,l in enumerate(open('wiki/topics/model-comparison.md',encoding='utf-8'),1) if l.startswith('|') for c in re.sub(r'\]\([^)]*\)',']',l).split('|') if len(c)>150]"
  ```

  有輸出且非引用來源格 → 違規，先短語化再收工

## feature-radar 判斷

新模型發布 = 使用者可 `--model` 選用 → **須回報主編新增 feature-radar 條目**。

純模型評測論文或研究報告（無可用介面）→ **不進 feature-radar**，記於模型頁即可。

## 模型 記者回報

來源歸因：[每筆一行 or 無]
