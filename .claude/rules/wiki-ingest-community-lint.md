# Wiki Ingest — 社群記者 Lint 指南

`/wiki-lint` 時由社群記者載入，處理三項任務：`community-tech-tools.md` 策展 + `community-tech-patterns.md` 模式淘汰審查 + `community-pattern-trends.md` 趨勢頁週更。每日 ingest 不需讀此檔。

## community-tech-tools 結構 `[加入: 2026-06-19，改版: 2026-09-02]`

**此頁已脫離每日 ingest，全部只在 `/wiki-lint` 維護。** 讀者動線：`我卡在這裡（症狀決策表）→ 推薦細節 → 不綁症狀的精選 → 工具目錄`。2026-09-02 改版：原「痛點洞察＋值得關注」兩層併為單一決策表——痛點格塞 9 個工具名等於沒有推薦（改版依據見 `wiki/log.md` 2026-09-02 相關條目）。

| 區塊 | 性質 | 紀律 |
|------|------|------|
| `## 我卡在這裡` | 症狀 → 首選決策表，四欄固定：`我的症狀｜先裝這個｜什麼時候改裝別的｜證據` | **首選唯一**；分界句寫**讀者處境**（「要團隊共享」「不能接受過代理層」），不寫工具形態（工具改版會讓形態句靜默失真）；證據值**必帶判定日**；答不出首選就誠實寫 `—` 附理由 |
| `**推薦細節**` | 表下細節區 | 含數字（%／倍／星數）的條列**必帶日期**（`check_tools_page.py` 會驗）；🔌 proxy 類必附安全／政策註記 |
| `## 不綁症狀的精選` | 規模或門檻值得認識、但不對應症狀者 | 少量（≤6 列），附證據＋日期 |
| `## 🧩 Skills 速查` `[加入: 2026-09-02]` | 社群 skill 的 coding 用途索引，分組：寫碼紀律／產出與呈現／領域資料／Codebase 理解 | 收錄 Skills 類條目時**同時歸組入本節**（一行：名＋證據＋一句話）；官方 skill 不入本節（兩條官方軸在 [[topics/coding-workflow-guide]]，互補不重複）；分享基建與彙整清單不入。**「Codebase 理解」組達 ≥3 工具時按知識傳承三工種細分**（給人·探索式理解／給人·交付級圖表／給 agent·索引；分類依據見 `wiki/log.md` 2026-09-02 Query）——C 窗佇列中的 Understand-Anything／archify／codegraph 入庫後適用，codegraph 入庫時並評估與 graphify 的對比列 `[加入: 2026-09-02]` |
| `## 工具目錄` | 完整收錄列表（依日期倒序） | 沿用採用符號（與證據**不同軸**，圖例明示）；⏳ 不長期保留 |

**首選維護鐵則：**
- 首選**只在出現新證據**（實測、負評、官方化、棄坑）時更換，不為輪替而換（同 feature-radar 防霸榜哲學）
- 決策表出口三分流：官方已內建 → wikilink [[feature-radar]]；答案是模式不是工具 → wikilink [[topics/community-tech-patterns]]；具體工具 → 本頁。出口**連頁不連錨**（錨點會隨蒸餾／改名腐化）
- 症狀列的證據為 🟢 或首選被更換時，該列須複查分界句前提是否仍成立

## community-tech-tools 策展規則 `[加入: 2026-06-19]`

**步驟：**
1. **來源**：讀取距今 7–14 天的 `news/*.md`，這是工具的唯一原始資料來源
2. **萃取達標工具寫入 `## 工具目錄`**（門檻，滿足其一）：
   - 達對照表（`.claude/rules/wiki-reporter-shared.md`）**中**門檻（HN 評論數已隨日報 summary 提供）
   - 同一天被至少 2 個獨立來源報導
   - 已證明採用（多次出現、有實際使用回饋）
   - **排除**：無公開 repo / demo / 連結；純商業廣告；僅媒體報導（media 類）而無任何社群來源（HN/Reddit/GitHub/dev.to）討論
3. **欄位** `| 工具 | 類型 | 採用 | 首次出現 | 簡介 |`：有 URL → `[**Tool**](url)`，URL 從日報原文擷取；採用預設 `⚡`，score ≥ 100 或評論 ≥ 20 維持 `⚡`，廣泛採用才給 `✅`
   - 寫入前查表去重：同名 / 同 URL 已存在則更新該筆，不新增重複列
4. **汰除**：採用降為 ❌、或距今 > 30 天仍為 ⏳ 無後續者，移除該列（git history 留存）。「無後續」的判定**用共用腳本查，不要臨場手刻 grep** `[加入: 2026-08-29]`：`python scripts/news_mentions.py --since 4w "英文名" "中文譯名"`。它強制 ≥2 別名、拒絕過寬詞、且輸出命中原文行——三者分別擋掉漏抓、假命中、與「只看次數就下結論」。理由與實例見該腳本檔頭。**現為決策表首選或次選的工具，其目錄列不隨汰除規則移除**（推薦的證據底不能被搬空）
5. **同步 `## 我卡在這裡`** `[改版: 2026-09-02]`：新工具能解掉既有症狀、或既有首選出現否定證據時，才動決策表對應列（多數週不動）；新症狀成立門檻＝≥2 筆獨立需求證據（抱怨/求助型條目），單一抱怨不開列

## community-tech-patterns 模式淘汰審查 `[加入: 2026-06-28]`

每次 `/wiki-lint` 時對 `wiki/topics/community-tech-patterns.md` 執行以下審查（dry run 先回報，確認後執行）。

**淘汰標準（滿足其一即列出）：**

| 條件 | 說明 |
|------|------|
| **官方化** | 模式描述的 workaround 已被 Claude Code 官方功能取代（對照 `wiki/feature-radar.md` 與 `wiki/entities/claude-code.md`）|
| **60 天沉寂** | 近 60 天日報未提及此模式或相關技術，且成熟度 ≤ ⚡ |
| **否定驗證** | 日報或 `community-tech-discussions.md` 出現「此模式有問題 / 過時」的明確社群共識 |
| **版本過期** | 模式明確綁定某已 deprecated 版本號 |

**處理原則：**
- 完全被取代 → 刪除
- 部分被取代（如底層官方化、上層應用層未取代）→ 拆分，刪除已取代部分，保留未取代部分並加「官方趨勢觀察」說明
- 主題相近的多條條目 → 合併為「同目標不同做法對照」，保留各自來源連結
- 沉寂但概念仍有效 → 保留，不因沉寂單獨刪除

**Dry run 回報格式：**
```
## community-tech-patterns 淘汰審查

### 建議淘汰（共 N 條）
| 模式名稱 | 所在區塊 | 觸發標準 | 說明 |

### 建議合併（共 N 組）
| 模式組合 | 合併理由 |

### 保留（共 N 條）
[列出保留理由]

### 無法判斷（共 N 條）
[列出需人工確認的項目與不確定點]
```

**回報後等待使用者確認，再執行實際修改。**

## community-large-codebase-workflow 週更整線重寫 `[加入: 2026-08-05，改版: 2026-08-15]`

`community-large-codebase-workflow.md` 是**週更**頁（每日 ingest 只在 patterns 節點標 `**主線：**` tag，不寫此頁——規則見 `.claude/rules/wiki-ingest-community.md`「主線 tag 規則」）。每次 `/wiki-lint`：

1. **撈料**：`Grep "\*\*主線：\*\* [^—]" wiki/topics/community-tech-patterns.md`，取近 7 天（補跑時取上次更新日以來）帶 tag 的節點；另掃近 7 天填 `—` 但「與既有模式的關係」提到主線的節點，重判一次
2. **整線重寫，不 append**：對每條有新節點的線（並行規模／Context 管理／索引記憶／除錯分工），讀該線現有全文＋新節點，**重寫**該線；沒新節點的線不動
3. **每條線固定四層、≤ 30 行**（硬上限，逼「換掉舊結論」而非「往下加」）：

   ```
   ### N. 線名：一句話問題
   **現在的答案**            ← ≤ 3 條可執行結論
   **🧰 現在就能下的解**     ← 1 行，連 [[topics/community-tech-tools]] 決策表對應症狀列 `[加入: 2026-09-02]`
   **還沒解決**              ← ≤ 2 句
   | 子問題 | 社群走到哪 | 代表實作 | 證據強度 |   ← 工具名只出現在這裡
   **為什麼會這樣**          ← ≤ 3 句機制散文，不列工具
   ```

   **🧰 行的紀律** `[加入: 2026-09-02，全站化: 2026-09-02]`：連頁＋引症狀句，不連錨（錨點會腐化）；只引決策表**首選**與必要分界，不複製工具細節（事實的家在 tools 頁）；引用的首選被更換時本行必須同步——症狀句對帳由 `scripts/check_tools_page.py` 機械驗（引錯句測試會紅），症狀列被移除時本行降為缺口態。**缺口態格式**：`—（決策表暫無對應列｜候選症狀：X）`。

   **🧰 全站維護（每輪策展三步，用既有資產不新造）** `[加入: 2026-09-02]`：
   1. **盤點 spoke**：`python scripts/wiki_graph.py explain topics/community-tech-tools` 看入邊（含節與行號）——哪些問題頁已連進來
   2. **找缺口**：`python scripts/wiki_graph.py sections "還沒解決"`（及 `sections "缺口"`）與步驟 1 差集——有問題段但無邊連入者，評估補 🧰 行或缺口態
   3. **聚合開列**：`grep -rn "候選症狀：" wiki/topics wiki/entities` ——**同一候選症狀出現於 ≥2 頁**即達決策表開新症狀列門檻（需求證據由問題頁自然餵入，取代臨場萃取）；開列後把各缺口態改為正式引用

   已鋪 spoke：large-codebase（4 線）、enterprise-cost-management、code-quality-decline；其他問題頁由對應記者按上述格式自行補（guide 屬功能記者，其「缺什麼」欄位形態不同，是否鋪由功能記者評估）。

   - 「代表實作」欄放工具／文章名，每格 ≤ 3 個，多的以「等，見 [[topics/community-tech-patterns]]」收尾；「證據強度」用 `多來源／單一實測／單一深度分析／已成趨勢／推論` 五值
   - 散文段不得出現日期開頭條列（`- 05-06 …`）或 `### YYYY-MM-DD`；日期只在需要錨定時括號附註
   - callout ≤ 2 句，寫「哪條線的答案變了」，不得含「大縫／小縫／漏縫補縫／縫合」等維運字眼
   - 摘要表「目前收斂點」欄與各線「現在的答案」第一條同步
4. **第五條線評估**：tag 填 `—` 但反覆出現的同類節點群 → 回報主編轉知 weekly-review 評估開線
5. 更新「最後更新」「最後新聞更新」；本週零新節點且結論未變 → 不動頁面

## 月度蒸餾與細節封存（patterns / discussions 技術彙整）`[加入: 2026-08-28]`

前 8 大頁佔全庫 60% 資訊量，全是 prepend-only 成長型；封存機制先前因「無量測、無提案端」半癱瘓。本機制以**蒸餾＋封存**取代單純搬走：主頁熬濃成重點層（閱讀性提升）、原始條目進 archive 證據層（一字不刪），搜尋動線變成「先命中重點頁，要細節再下鑽 archive」。

**候選門檻（兩者皆滿足才提案）：**
- 該 `### YYYY-MM` 月份分組距今 **≥ 3 個月**
- 該月條目**不再被活躍敘事引用**——主線頁「代表實作」欄、趨勢頁演進節點、討論表「衍生」欄均未指向該月條目；有 🌊延燒／🌋重燃狀態的討論其歷史月份**一律不蒸餾**（重燃需要上下文在場）

**Dry run 提案格式（回報主編轉呈使用者，確認後才執行）：**
```
## 月度蒸餾提案
| 頁面 | 月份 | 條目數 | 字元數 | 擬總結一句 | 引用檢查 |
```

**執行步驟（經確認後）：**
1. **封存**：把該月全部 `####` 原始條目**原文照搬** append 至對應 archive 頁的 `## YYYY-MM` 分組——`topics/community-tech-patterns-archive`／`topics/community-tech-discussions-archive`（首次蒸餾時建立：標頭領域同主頁、狀態 `resolved（封存頁）`、頂部 callout 說明「本頁為原始條目封存，重點層見主頁」，並回報主編補 `wiki/index.md` 列——index 同步檢查會驗）
2. **蒸餾**：主頁該月改寫為**月度總結 ≤ 15 行**——當月主要模式/討論、收斂結論、仍具引用價值的工具名，末行固定 `原始條目見 [[topics/community-tech-patterns-archive#YYYY-MM]]`（錨點建置會驗）
3. **引用回掃**：grep 全庫指向被搬條目錨點的 `[[頁#條目標題]]` 連結，改指 archive 對應錨點——蒸餾是搬位置＋熬濃，不是刪除，斷鏈即違規
4. 主頁只更新「最後更新」（非新聞性修改）

**節奏與上限：** 每次 lint 至多提案 2 個月份（漸進，不一次大搬家）；無達標月份 → 回報「無蒸餾候選」即可。

每次 `/wiki-lint` 時更新 `wiki/topics/community-pattern-trends.md`（週更，非每日）。

**趨勢成立門檻（同時滿足）：**
- ≥ 3 個獨立來源（不同社群帳號、不同媒體、不同工具）
- 首次出現距今 ≥ 14 天
- 至少 1 條 A 層（量化/可重現）或 B 層（機制完整）證據

**更新步驟：**
1. 讀取近 14 天 `news/*.md`，對照 `community-tech-patterns.md` 現有模式，偵測：
   - 現有趨勢有新節點加入（補充 `#### YYYY-MM-DD` 節點）
   - 趨勢成熟度升級（升格 📈 → stable 或標記進入 plateau）
   - 新趨勢達成立門檻（新增趨勢區塊）
   - 趨勢沉寂超過 30 天且無新節點（標記為「↘ 淡出」）
2. 每條趨勢的 `**對現有設計的啟示：**` 欄位若有新節點，同步更新啟示文字
3. 更新頁面 `**最後更新：**` 日期

**不更新情況：** 若近 14 天無新模式節點、無趨勢成熟度變化，保持頁面不動（不必要地更新日期會誤導讀者）。

**格式（新節點）：**
```markdown
#### YYYY-MM-DD
[一行說明新增的模式或事件，附 pattern 名稱]（🔥/🔥🔥/🔥🔥🔥）
```

## community-tech-tools 決策表驗收：3 跳自檢題 `[加入: 2026-09-02，取代原精選層提拔規則]`

原「值得關注的工具」精選層已於 2026-09-02 併入決策表與「不綁症狀的精選」，提拔規則廢止。取而代之：**每輪策展結束後重跑以下 3 題**（比照 `.claude/rules/wiki-ingest-models.md` F 條），從 `wiki/index.md` → 本頁 → 對應列，3 跳內須得到**單一工具名＋一句為什麼＋安裝形態**；落在兩列之間或多工具並列無從取捨 → 不合格，補分界再收工：

1. 「我跑大 repo，一天燒掉週配額，想先知道錢花在哪」→ 應命中「帳單爆了」列的單一首選（驗拆痛點：不得同時命中「context 撐爆」列）
2. 「三個 agent 在同一 repo 上跑，一直互相覆蓋改動」→ 應命中「互相覆蓋」列；若補述「隔離了但 commit 打架」→ 第三欄應接得住
3. 「它回報測試通過，我發現測試根本沒跑」→ 應命中「說做完了但沒做」列的單一首選

結果寫入回報；連續 2 輪同一題不合格 → 回報使用者檢討表結構。
