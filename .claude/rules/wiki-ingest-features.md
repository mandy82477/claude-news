## 程式開發實戰手冊維護 `[加入: 2026-08-08]`

`wiki/topics/coding-workflow-guide.md` 回答「我現在在做這件事，該下哪個 skill」。它有**兩條進料**：

| 進料 | 節奏 | 觸發邊 |
|---|---|---|
| 技能清冊與社群工具策展 | 🗓️ 週更，於 `/wiki-lint` 執行 | 本節下方「週更動作」——類別路由接不到，本節即其觸發邊 |
| **官方對既有功能的使用指南**（省 token、session 經營、設定建議，無新指令旗標）`[加入: 2026-08-16]` | 每日 ingest | 類別路由：日報條目分類為「功能」且屬使用指南型態，見 `.claude/rules/wiki-ingest.md`「分流鐵則：官方內容不是社群類的禁區」 |
| **本週 coding 亮點節＋「社群面待補」段補寫** `[加入: 2026-09-02]` | 🗓️ 週更，devpractice 記者於 `/wiki-lint` 5f 執行 | **不由你維護**——見 `.claude/rules/wiki-ingest-devpractice-lint.md`。你 lint 時發現該節內容異常，回報主編轉知，不自行改寫 |

**官方使用指南的寫入紀律 `[加入: 2026-08-16]`：** 寫進對應的流程階段節（如 token 經濟 → `## 2. 探索 codebase` 的「2a. 怎麼讀得省」），與該節既有的「官方的…」子節並列；**必附官方原文連結與發布日期**。它是本頁唯一可以來自新聞條目的內容——放行理由是它恰好滿足下方「不做的事」所要求的一切（有一手來源、會被更新、經得起查證），原本那句「不吃新聞條目」是拿**進料管道**當**可信度**的代理，擋錯了人（2026-08-15 教訓見 `.claude/rules/wiki-ingest.md` 分流鐵則）。社群做法仍走週更策展，不因本條放行而改。

**軸線鐵則：** 以**工程流程階段**為軸（設計→實作→審查→測試→部署→事故→償還），**不得改以開發領域（嵌入式／遊戲／資料工程）分欄或分列**。官方技能本身就不是按領域切的，照領域組織會產出大量空格；領域差異只放在「領域注意」欄，且**僅在有具體依據時填寫，無依據留 `—`**——此欄最容易被通用工程常識灌水，而通用常識不是本庫查證所得，不得寫成像有來源的樣子。

**週更動作：**
1. 讀 `Official Skills` 來源近 7 天條目（`src/news_aggregator/sources/official_skills_repos.py` 偵測到的清冊異動）；有新增／移除的 skill → 更新對應表列，並同步 `entities/claude-skills` 生態動態
2. 官方新 skill 若屬工程流程階段 → 補入流程表；屬產出物格式 → 補入格式表；屬非工程用途 → 只記在 `entities/claude-skills`，不進本頁
3. 檢查「官方涵蓋不到的地方」是否已被新官方 skill 覆蓋；已覆蓋者從該節移除並回報主編同步 `official-community-gap` 矩陣
4. **「深入」節的技巧回訪**：比對近 7 天 `community-tech-patterns` 新節點，判斷有無（a）解掉「探索時常撞到的問題」表中某一列、（b）取代該列現有做法、（c）為 format 線補上第三個獨立節點。有則更新該列並調整訊號欄；無則不動——**這是為了讓「現有做法」不會停在建頁當天的答案**
5. 清冊查證日更新於「參考來源」；本頁為清冊性更新，**不動「最後新聞更新」**

**不做的事：** 不從通用工程知識補內容（無來源、不會被更新，且會讓讀者誤以為經查證）；不記錄各 skill 的內部實作細節（那屬上游 repo，會腐爛）。

## feature-radar 准入定義 `[加入: 2026-06-15]`

feature-radar 只收**使用者可實際取用、呼叫、設定或執行的官方產物**。收錄前先問：

> 「使用者拿這個能做什麼**具體操作**？」答不出來 → 不收錄。

✅ **屬於功能（收錄）：** 新模型 / 模型能力（可 `--model` 選用）、新指令 / 旗標 / 設定項、新 API / SDK 變更 / 棄用、影響使用方式的 Breaking change。

❌ **不屬於功能（不收錄，改投對應頁面）：**

| 類型 | 範例 | 改投 |
|------|------|------|
| 研究成果 / 論文（無可用介面）| 化學 NMR 分析 | 對應 entities 或略過 |
| 公益 / CSR / 組織 / 人事 | Claude Corps | `topics/anthropic-business` |
| 定價 / 計費 / 配額政策 | Agent SDK 計費切割 | `entities/pricing` |
| 商業合作 / 融資 | TCS / DXC 合作 | `topics/anthropic-business` |
| 純策略表態（無新功能）| HTML 輸出背書 | `topics/community-tech-discussions` 或略過 |

> 模型本身算功能（可選用）；模型的**定價**歸 `entities/pricing`。

### 否定證據也要有路回來 `[加入: 2026-09-05]`

**收到主編轉知的**日報條目若拿某個官方功能當對照組，宣稱替代方案在成本、準度或速度上更好（無論該條目被分類成社群、是否達收錄標準），在對應 `entities/` 頁的細節區記一行，**必附證據等級與缺什麼**（如「單一貼文，未附測試方法」），並於回報「同步自查」欄註明來源日期。**不進 feature-radar、不改熱度以外的評級**——它是讀者判斷「值不值得」的唯一反向材料，不是功能異動。發訊端規則見 `.claude/rules/wiki-ingest-community.md`「官方功能的負向對照要回流」。（立法依據見沿革檔 2026-09-05）

**新功能條目格式（回報給主編時附上此格式）：**
```markdown
### 功能名稱
**發布：** YYYY-MM-DD（版本號） | **熱度：** 🔥🔥🔥 | **試用價值：** ⚡ 有條件推薦 | **狀態：** Research Preview

**是什麼：** 一句話描述功能用途。

**為何熱：** 社群反應、討論來源、工具跟進情況。

**現在要試嗎：** 適合誰立即用 / 不適合誰（先等等）。

**快速上手：**
\```
最小可用指令或配置範例
\```

**注意事項：** 已知限制或使用前提。
```

### 熱度降溫：它不是棘輪 `[加入: 2026-08-20]`

熱度值必須會衰減，否則全覽表的熱度欄會誤導：讀者按熱度排序選功能，會選到已經沒人在討論的條目。（教訓見沿革檔 2026-08-20）

- **判定**：`/wiki-lint` 5a 由主編執行——對每個追蹤中的功能查近 4 週日報；零命中則熱度 −1 格。**用共用腳本查，不要臨場手刻 grep** `[加入: 2026-08-29]`：`python scripts/news_mentions.py --since 4w "英文名" "中文譯名"`。它強制 ≥2 別名、拒絕過寬詞、且輸出命中原文行——三者分別擋掉漏抓、假命中、與「只看次數就下結論」。理由與實例見該腳本檔頭。
- **下限 🔥**：降到 🔥 就停，不再往下（曾經熱過是事實，歸零會讓歷史看起來像沒發生過）
- **同步**：熱度是跨頁值，radar 降一格就要同步對應 `entities/` 頁的「熱度與試用價值」表——**單邊下修是矛盾的來源**（實例見沿革檔 2026-08-01）
- **不降的例外**：狀態為「⏰ 倒數中」或本輪熱度／試用價值有變動者，本輪不降

### ⏳ 觀望是有期限的判斷，不是停車場 `[加入: 2026-08-28]`

「⏳ 觀望」對讀者的承諾是「**還在看，之後會有結論**」。若一條目標了觀望就再也沒人回頭，那個標籤實際上在說謊——讀者以為在等，其實沒人在等。

- **判定**：`/wiki-lint` 5a 執行——全覽表中標 ⏳ 且**發布日距今 > 90 天**者，逐一查日報有無後續
- **查證方法（強制，否則結論不可信）`[加入: 2026-08-28]`**：
  1. **用 `scripts/news_mentions.py` 查，不要臨場手刻 grep** `[改版: 2026-08-29]`——上述三道防線已寫進腳本並有回歸測試（`src/tests/test_news_mentions.py` 用的正是本次踩到的兩個真實案例）
  2. **多組別名**：英文原名、單一關鍵詞、**中文譯名**都要給。日報是繁中寫的，只用英文全名比對必然漏抓（腳本強制 ≥2 別名）
  3. **逐條看腳本輸出的命中原文行**，確認是否真指該功能——同名媒體、同名產品會製造假命中
  4. 缺任一步都會得到相反的結論——**漏抓會把活著的功能判死，假命中會把死的判活**
- **三選一，不得留原狀**：

  | 情況 | 處置 |
  |---|---|
  | 查到後續（實測、跟進報導、狀態變更）| 依證據升 ⚡／✅，或降 ❌ |
  | 零後續、細節從未公布 | 保留 ⏳，但**在條目名後加註「（YYYY-MM-DD 公告，此後未見後續報導）」**，熱度同時降至 🔥 |
  | 仍在合理等待（如已公告 GA 日期）| 保留 ⏳，**明寫在等什麼、預期何時**，否則視同上一列 |

- **90 天而非 60 天**：60 天會抓到還在合理觀望期的近期條目。90 天是「公告後一季仍無下文」，此時「還在看」已不成立
- **註記不是懲罰，是還原事實**：讀者要的是「這個能不能用」，「公告過但沒下文」本身就是答案——比掛著 🔥🔥🔥🔥 的觀望誠實得多
- **已加註者不重複處置**：條目名已帶「（YYYY-MM-DD 公告，此後未見後續報導）」註記者，本輪跳過，**除非近 4 週出現後續**——有後續就移除註記並依證據重新評級。沒有這條，同一批條目會每週被重新抓一次，變成固定假警報，而固定假警報會讓人開始略過整個檢查。（教訓見沿革檔 2026-08-28）註記寫的是公告日不是天數，所以本輪跳過不會讓數字停在加註那天。`[改版: 2026-09-06]`

**新增 `docs/rules-changelog/wiki-ingest-features.md` 的 `## 2026-09-06` 段**，收 (a)(b) 兩段敘事：熱度三處副本的實測數字、「公告後 N 天」搭配「不重複處置」必然愈久愈假（radar 教訓：曾寫 102 天實為 111 天）。

### 新條目必須同時補全覽表一列 `[加入: 2026-08-09]`

`## 🆕 最新功能` 的詳細條目與 `## 📋 功能全覽表` 是**同一件事的兩個入口**——全覽表是讀者掃描用的索引，詳細條目是內文。**只寫詳細條目不補表列，該功能在索引上等於不存在**（教訓見沿革檔 2026-08-09）。

回報新條目給主編時，一併附上表列（欄位固定五欄，依發布日期插入正確位置，最新在上）：

```markdown
| **功能名稱**（括號內一句話說明，含版本／平台／關鍵旗標） | YYYY-MM-DD | 🔥🔥🔥 | ⚡ 有條件推薦 | 正式發布 |
```

- **發布日期欄**：尚未生效的公告寫 `YYYY-MM-DD 生效（MM-DD 公告）`，讓讀者一眼看出是未來式
- **熱度／試用價值欄**：`[加入: 2026-09-06]` **在 feature-radar 頁內，熱度與試用價值只寫在 `## 📋 功能全覽表`**（詳細條目標頭只留「發布」與「狀態」，推薦節不寫熱度括號）。**entities 頁的 `## 熱度與試用價值` 表不受本條影響**，它是跨頁常態值，同步規則見本檔「熱度降溫」——同一個值住兩處就會有兩個答案（2026-09-06 實測：名稱配得起來的 25 對中 10 對打架，另 66 列名稱不同到無法機械配對——所以看守單一家，不做配對比對）。（教訓見沿革檔 2026-09-06）
- **狀態欄**：`正式發布` / `Beta（範圍）` / `官方公告（尚未生效）` / `Research Preview` / `正式發布（安全修復）`

> `[加入: 2026-09-06]` radar 內部只有全覽表一個家，降格改一處即可；entities 頁的熱度表照舊同步。

**ingest 結尾對帳（強制）：** 數當月 `### ` 詳細條目數與全覽表中該月列數，兩者必須相等；不等就補齊再收工，並在回報「同步自查」欄寫出兩個數字。舊月份因詳細條目封存而表列較多屬正常，只對帳**當月**。

## ⭐ 這禮拜值得跟的三件 自動更新規則 `[加入: 2026-06-20，改名: 2026-09-06]`

每次 ingest 後，主編在彙整 `wiki/feature-radar.md` 時一併覆寫 `## ⭐ 這禮拜值得跟的三件` section（原節名「本週推薦」，2026-09-06 P2 頁面健檢改名）。

**選取邏輯（依序）：**
1. **先過時間閘**（`[加入: 2026-08-08]`）：候選池 = 發布日期距今 ≤ 30 天、**或**本次 ingest 熱度／試用價值有變動的條目。熱度只加不減，沒有時間閘的話候選池會固化成「歷代名人堂」，讓一個叫「這禮拜值得跟的三件」的區塊長期掛數月前的條目
2. 從候選池選出熱度 🔥🔥🔥🔥 以上、試用價值 ✅ 或 ⚡ 的條目
3. **排序改版 `[改版: 2026-09-06]`**：第一條固定是「你不動它、它也會改變你行為」的那一件（預設值改變、預設模型換代），其餘依熱度降序；同熱度時 ✅ 優先於 ⚡，仍同分時較新發布者優先
4. 取前 3 名；候選不足 3 條時，時間閘放寬至 60 天再取一輪，仍不足則只列實際達標的條目（**不補舊條目湊數**）

**防霸榜規則（`[改版: 2026-08-08]`）：** 若某條目已連續上榜超過 7 天，且今日 ingest 未更新其熱度或試用價值，檢查候選池有無**更新且達標**的替補：

| 情況 | 動作 |
|------|------|
| 有合格替補（過時間閘、達 🔥🔥🔥🔥+） | 換上替補 |
| 無合格替補 | **維持現有推薦不動**，並把 `> 本週無新達標功能，維持上週推薦（最後輪替：YYYY-MM-DD）` 這行寫進頁面的 `%% … %% `（維運備忘，不上讀者正文，`[改版: 2026-09-06]`；教訓見沿革檔 2026-09-06） |

> 硬性禁止：不得為了滿足輪替而換上「比現有更舊」的條目——本節的讀者契約是「這禮拜有什麼值得跟」，誠實說沒有優於推一個三個月前的功能。連續 3 週出現「無新達標功能」時，在回報中標「⚠️ 本節連續 3 週無替補，建議檢討 🔥🔥🔥🔥 門檻是否過高」轉知主編。

**判準句（三條全過才入表）：** ① 狀態為 🔴 或 ⛔，且是缺陷不是功能請求——GitHub 標 `enhancement` 者不入表，還沒做的東西不會咬你；② 「誰會遇到」欄必須寫出產品或平台限定（Cowork／Desktop／Linux／Windows／企業 SSO），寫不出限定就是所有人；③ 寫得出「你能做什麼」，繞法或「無繞法」都算，兩者皆答不出的條目留在下方分組。**上限 8 列。排序：** 不可自行復原者（資料遺失、工作遺失、帳單、安全）在最上，其餘依「誰會遇到」的範圍由寬到窄。**退場：** 翻 ✅ 或官方給出替代即移出；連續 90 天無新回報且非資料完整性類者移出，並在原條目末加「（已移出結論表，YYYY-MM-DD）」。

## 版本更新收錄判斷

版本號本身不是收錄理由，**必須有至少一項使用者端的具體異動**才進 feature-radar：

| 情況 | 判斷 | 處置 |
|------|------|------|
| 純 bug fix / reliability（無具體功能說明）| ❌ 不收錄 | 記入 `entities/claude-code` 版本表 |
| 內部基礎設施更新 | ❌ 不收錄 | 略過 |
| 單一 bug 的 hotfix（已屬於另一功能的修正）| ❌ 不收錄 | 附記在對應功能條目「注意事項」 |
| 有新指令 / 新旗標 / Breaking change | ✅ 收錄 | 正常建立條目 |
| API 棄用 / 重大 SDK 變更 | ✅ 收錄 | 以「SDK / 棄用」為主題建立條目 |

## 1M 專頁的觸發邊 `[加入: 2026-08-30]`

`wiki/topics/long-context-1m.md` 是**衍生頁**——1M 相關的新聞條目會照舊被路由到 `entities/claude-code`（已知問題）或 `entities/pricing`（計費規則），**沒有任何條目會自己路由到這一頁**。依 `.claude/rules/wiki-ingest-format.md`「建頁時必須確認觸發邊」，此處登記明文觸發邊，否則該頁會孤兒化。

**每次 ingest：** 你為 claude-code 或（經商業記者）pricing 寫入的條目，只要涉及下列任一項，**同時**更新本頁：

| 條目涉及 | 本頁要動的地方 |
|---|---|
| 長脈絡費率、世代分界、1M 是否加價 | 「你的 1M 會不會加價」表 |
| 1M 的預設行為、開關、model picker、`[1m]` 變體 | 「你控制不了的地方」表＋狀態欄 |
| **1M 的可見性**——狀態列／`/model`／設定畫面顯示的 context 上限與實際不符 `[加入: 2026-08-30]` | 同上；「看不出自己在不在 1M 上」也是控制權缺口的一種，不因為它「只是顯示問題」而排除 |
| 0% 用量卻被收費、獨立計費通道、`ANTHROPIC_API_KEY` 走 API 通道 | 「帳單對不上時怎麼判」表 |
| 以上任一 | `## 時序` prepend 一則，更新兩個日期欄位 |

**紀律：** 本頁只放「1M 這個旋鈕本身」。單一模型的費率數字屬 [[entities/pricing]]、選型建議屬 [[topics/model-comparison]]、單條 issue 的完整脈絡留在 `entities/` 原頁——本頁引 wikilink，不複製（同 `wiki/CLAUDE.md`「每個事實只有一個家」）。

**若某條目只影響費率數字而與 1M 無關**（如 Opus 5 調價），不動本頁。
