# Wiki Ingest 格式規則

執行 `/wiki-ingest`、`/wiki-lint`、`/news-pipeline` 時讀取此檔案。
包含所有格式模板、欄位規則、品質標準。一般 wiki 查詢無需讀取。

---

## 日報格式（news/YYYY-MM-DD.md 的五個區塊）

| 區塊 | 內容 |
|------|------|
| 📌 今日聚焦 | 3–5 點條列總結，標籤：重大事件 / 持續追蹤 / 新工具 / 社群趨勢 / 風險警示 |
| ⭐ 重點話題 | 跨多來源同時出現或引發大量討論的項目（2–5 則） |
| 🔧 技術更新 | 模型發布、功能更新、API/SDK 變更、官方公告 |
| 💬 技術熱度討論 | 社群討論、工具分享、開發者心得，附情緒標籤 |
| 💰 付費方案動態 | 定價、配額、Token 費用 |

---

## 決策框架：新建頁面類型

- **具體事物**（模型/工具/人物/產品）有足夠描述 → 當天建 entities/ 頁
- **現象/爭議/趨勢** 且 log.md 顯示昨天也出現 → 建 topics/ 頁
- **現象/爭議/趨勢** 今天首次出現 → 暫記於相關 entities/ 歷史，明天再評估

## entities/ 頁面格式模板 `[加入: 2026-04-25]`

功能類型（`類型: feature`）且熱度 ≥ 🔥🔥🔥，必須含 `## 熱度與試用價值` 及 `## 使用指南` 區塊。

```markdown
# 實體名稱

**類型：** model / feature / person / product / policy / event
**狀態：** active / deprecated / rumoured / resolved
**首次出現：** YYYY-MM-DD
**最後更新：** YYYY-MM-DD

## 現況

## 熱度與試用價值（feature 類型且熱度 ≥ 🔥🔥🔥 必填）

| 項目 | 評分 |
|------|------|
| 社群熱度 | 🔥🔥🔥 |
| 試用價值 | ✅ / ⚡ / ⏳ / ❌ |
| 最適合 | 適用場景 |
| 不適合 | 不適用場景 |

> 詳細最新熱度見 [[feature-radar]]

## 使用指南（feature 類型且有具體用法 必填）

## 核心功能
## 相關議題
## 參考來源
## 歷史記錄
```

## topics/ 頁面格式模板 `[加入: 2026-04-25]`

```markdown
# 議題名稱

**狀態：** ongoing / resolved / monitoring
**開始日期：** YYYY-MM-DD
**最後更新：** YYYY-MM-DD

## 摘要
## 技術彙整
## 目前結論
## 相關實體
## 時序
```

**技術彙整** 區塊：每次 ingest 後累積，條列技術機制、已知限制、workaround，不重複已有條目。議題解決後移至 entities/ 作為歷史記錄。

## feature-radar.md 更新規則 `[加入: 2026-05-13]`

| 情況 | 動作 |
|------|------|
| 日報出現新的官方功能（🔧 或官方公告） | 在「最新功能」區塊新增條目 + 更新全覽表 |
| 已追蹤功能再次出現（討論、工具跟進、問題） | 熱度 +1 格（上限 🔥🔥🔥🔥🔥） |
| 出現多個正面使用案例 | 試用價值升級（⏳→⚡→✅） |
| 出現重大 bug 或集中負評 | 試用價值降級（✅→⚡→⏳→❌） |
| 功能從 Preview 升格正式發布 | 考慮升為 ✅，更新狀態欄 |

**新功能條目格式：**
```markdown
### 功能名稱
**發布：** YYYY-MM-DD（版本號） | **熱度：** 🔥🔥🔥 | **試用價值：** ⚡ 有條件推薦 | **狀態：** Research Preview

**是什麼：** 一句話描述功能用途。

**為何熱：** 社群反應、討論來源、工具跟進情況。

**快速上手：**
\```
最小可用指令或配置範例
\```

**注意事項：** 已知限制或使用前提。
```

功能類型判斷：有具體指令/API → 必須提供「快速上手」；僅公告無用法 → 標「⏳ 觀望」；負評主導 → 標「❌ 暫不推薦」。

## community-tech-tools 工具新增規則 `[加入: 2026-05-20]`

**入選門檻（滿足其一）：**
- HN score ≥ 30，或 HN 評論數 ≥ 5
- Show HN 投稿（自動入選，無論分數）
- 同一天被至少 2 個獨立來源報導

**排除條件（優先於入選）：**
- 無公開 repo、無 demo、無可用連結（純商業廣告）
- 只出現在 Google News 且無 HN/Reddit 對應討論

**表格欄位：** `| 工具 | 類型 | 採用 | 首次出現 | 簡介 |`
- 有 URL → `[**ToolName**](url)`；無 URL → `**ToolName**`
- 新工具預設 `⏳ 觀望中`；score ≥ 100 或評論 ≥ 20 → `⚡`
- URL 直接從當天日報原文中擷取

**每次 ingest 後同步更新 `## 痛點洞察` 表格：**
- 新工具歸屬某痛點時，更新 `代表工具` 欄與 `近期工具` 欄
- 狀態：≤ 14 天有新工具 → 🔥；> 14 天 → 🌙；Anthropic 發布官方功能 → ✅；工具潮退有穩定最佳實踐 → ⚡

## enterprise-tool-tracker 更新規則 `[加入: 2026-05-26]`

**觸發條件（滿足其一即更新）：**
- 具名企業採用、擴大、縮減或停用某 AI 編碼工具
- 企業工具切換報導（含有規模描述的匿名企業，如「某頂尖科技公司」）
- 企業 AI 工具預算或成本相關的具名案例

**表格欄位格式（7 欄，順序固定，build_web.py 依此解析）：**
`| 企業 | 規模 | AI 編碼工具 | 狀態 | 事件日期 | 備註 | 確認日期 |`
- **狀態：** ✅ 使用中 ／ ⚠️ 縮減中 ／ 🔄 切換中 ／ ❌ 已退出 ／ ❓ 未確認
- **事件日期：** YYYY-MM-DD（不確定填 `—`）
- **確認日期：** 媒體報導或消息來源的日期

**更新動作：**
1. 在「企業工具使用現況」表格新增或更新企業列
2. 更新「工具競爭態勢」表格受影響工具的企業採用數與趨勢
3. 在「時序」區塊 prepend 新事件（`### YYYY-MM-DD` + 一行說明）
4. 更新頁面「最後更新」日期

**不在此頁追蹤：**個人開發者趨勢、成本分析細節、無具名的匿名案例。

## community-tech-patterns ↔ community-tech-discussions 雙向連結規則 `[加入: 2026-05-16]`

新增工具至 `community-tech-patterns.md` 時，若靈感明確來自 discussions.md 的某個討論，同步在 discussions.md 的 `熱門討論` 表格對應列的 `衍生` 欄填入工具名稱（若已有則逗號追加）。

`熱門討論` 表格 `模式` 欄規則：

| 狀況 | 模式 |
|------|------|
| 今天首次出現 | ☄️閃現 |
| 第 3 天以上持續出現 | 🌊延燒 |
| 討論達成共識後收束 | 🌸落幕 |
| `首見` 距今 > 7 天後重新出現 | 🌋重燃（在核心論點補「（重燃原因：…）」） |
| 表中存在但近期無新進展，熱度 ≤ 🔥 | 🌙靜候 |

重燃偵測：直接查 `熱門討論` 表格的 `首見` 欄，不需讀取 log.md。

## community-tech-discussions 技術彙整書寫規則 `[加入: 2026-05-20]`

**格式：**
```markdown
### 討論主題名稱（YYYY-MM-DD）

- **來源：** 原始文章標題（平台，作者）
- **核心論點：** 一句話摘要
- **關鍵回響：**（選填，有則記）
  - 📝 支持：…（標題，來源）
  - 📝 反駁：…（標題，來源）
  - 🧪 跟進實測：…（標題，來源，結論一句話）
- **收斂結論：**（若討論已有共識）…
```

**新條目插入位置：** 永遠插入 `## 技術彙整` 標題的**正下方**（最新在最上方），不可加在末尾。

**防過度推論：** 推導出的結論必須標注「（推論）」，不可直接寫成事實。常見錯誤：把「部分社群認為」寫成「社群共識」。

## Wiki 頁面呈現品質標準 `[加入: 2026-05-15]`

### 必須修復（ingest 完成前不得跳過）

| 項目 | 判斷方式 | 修復動作 |
|------|---------|---------|
| **摘要可獨立閱讀** | `## 現況`/`## 摘要` 前 160 字能讓不熟悉背景的讀者理解頁面主題 | 改寫摘要段落 |
| **關鍵資訊前置** | 最重要的事實出現在頁面前 1/3 | 將核心表格或結論移至前段 |
| **熱度表格緊接摘要** | 熱度統計表格緊接在 `## 摘要`/`## 現況` 之後，不可置於末尾 | 移動表格區塊 |
| **無 LLM 專屬指令** | 正文不含「請執行」「下一步」「若日報出現…」等操作語句 | 移至 CLAUDE.md 或刪除 |

### 警示觸發重構（超過閾值時嘗試修復；工作量過大則記錄 log.md 待辦）

| 警示條件 | 閾值 | 重構方向 |
|---------|------|---------|
| 頁面過長 | > 200 行 | 按主題分組，考慮拆分子頁面 |
| 事件流堆積 | 連續 8 個以上 `### YYYY-MM-DD` 無主題分組 | 合併為主題段落 |
| 缺少結構化 | 方案比較以純段落表達 | 改為 Markdown 表格 |
| 表格不可排序 | 欄位值格式不一致 | 統一日期、熱度、狀態符號格式 |
| 摘要缺失 | `## 現況`/`## 摘要` 空白 | 從頁面內容萃取補寫 |

### ingest 結尾強制輸出（Step 9 核對清單必須包含此欄）

```
| 呈現品質審查 | 每頁：✅ 通過 / ⚠️ 已修復（說明）/ 📋 已記錄待辦（說明問題）|
```

## 大型檔案讀取策略

頁面 > 300 行時，避免一次全讀：
1. 先用 Grep 搜尋目標區塊標題，取得行號範圍
2. 用 `Read` + `offset`/`limit` 只讀取需要的段落
3. 同一次 ingest 中多個無關頁面的更新，在單一訊息中平行發出多個 Edit 呼叫

典型大型頁面：`community-tech-patterns.md`、`community-tech-timeline.md`、`claude-code.md`
