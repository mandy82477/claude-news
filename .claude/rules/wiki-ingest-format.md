# Wiki 頁面格式規則

建立新頁面、或需確認格式規範時讀取此檔案。

---

## 決策框架：新建頁面類型

- **具體事物**（模型/工具/人物/產品）有足夠描述 → 當天建 entities/ 頁
- **現象/爭議/趨勢** 且 log.md 顯示昨天也出現 → 建 topics/ 頁
- **現象/爭議/趨勢** 今天首次出現 → 暫記於相關 entities/ 歷史，明天再評估
- **entities＝有專有名詞的具體事物；topics＝多方參與的現象/故事。更新頻率不是分類依據**——entities 也會每日更新

**建頁時必須確認觸發邊 `[加入: 2026-08-05]`：** 新頁建立前先判斷它吃什麼——

| 頁面吃什麼 | 觸發邊 | 建頁時要做的事 |
|---|---|---|
| **新聞條目**（一般 entities/topics） | 類別路由即觸發：日報條目分類 → 記者更新對應頁 | 無需額外登記，動態認領條款自然覆蓋 |
| **主題延伸到 Claude/Anthropic 之外**（競品、他家實驗室、產業現象） | 類別路由**只接得到「標題／tag 有提到 Claude/Anthropic」那一半**——12 個來源全部在來源端綁定關鍵字，`filter.py` 對 Google News 再加一道標題閘 | **必須寫 `**蒐集邊界：**` 欄位**（見下方「蒐集邊界欄位」），誠實告訴讀者哪些會漏；若該主題值得補抓，另評估申請 `src/news_aggregator/sources/topic_watch.json` 的定向 query |
| **別的頁面／跨記者彙整**（衍生頁：縫合層、策展層、趨勢層） | 類別路由**接不到**——沒有新聞會路由到它 | **必須同步在對應規則檔登記明文觸發邊**（daily 順手規則或 lint 週更規則），未登記不得建頁。記者無權改規則檔 → 在回報中標「⚠️ 需主編登記觸發邊：[頁名＋建議節奏]」，由主編層執行 |

> 教訓：`community-large-codebase-workflow` 2026-07-26 建頁時未登記觸發邊，僅靠「領域＝🌐 社群」概括條款覆蓋（所有權≠會被更新），孤兒化 10 天——patterns 持續進節點、主線零縫合；補上 daily 小縫後又因記者每天只看一個節點、只能往段尾加句，兩週把綜合頁長回 log，2026-08-15 改為 daily 標 tag＋weekly 整線重寫。既有衍生頁的觸發邊清冊見 `wiki/CLAUDE.md` 搜尋策略第 5 路。

### 蒐集邊界欄位 `[加入: 2026-08-13]`

主題延伸到 Claude/Anthropic 之外的頁面，**標頭「領域」之後必須加一行** `**蒐集邊界：**`，用讀者語言講清楚「本頁自動蒐集涵蓋什麼、什麼會漏」。

```
**蒐集邊界：** 以 Claude 為參照系的競品動態為主，另針對競品發布與定價定向補抓（每日至多 2 則）；競品自身未與 Claude 對比的發布可能延遲或缺漏。
```

> 教訓：`topics/ai-talent-flow` 自述「追蹤 AI 前沿實驗室**之間**的人才流動」，但 pipeline 結構上只收得到標題提及 Claude/Anthropic 的那一半。2026-08-05 Jeff Dean 等四人離開 Google 創辦 Discovery Loop——該主題史上最大事件——12 個來源零命中、漏 8 天，而讀者從頁面看不出有這個缺口。**承諾了結構上兌現不了的覆蓋範圍，且靜默地不完整**，與「查過確認沒有」和「沒人查」長得一樣是同一種病。

寫法紀律：**用讀者語言**，不得出現 `filter.py`、`topic_watch.json`、query 等實作名詞（此欄位會原樣顯示在網站詳頁標頭）；有定向補抓者要寫出每日上限，讓讀者知道那是補充而非完整覆蓋；**不得寫成「涵蓋全部」**——寫得出邊界才寫，寫不出代表還沒想清楚該頁吃什麼。

## entities/ 頁面格式模板 `[加入: 2026-04-25]`

功能類型（`類型: feature`）且熱度 ≥ 🔥🔥🔥，必須含 `## 熱度與試用價值` 及 `## 使用指南` 區塊。

```markdown
# 實體名稱

**類型：** model / feature / person / product / policy / event
**狀態：** active / beta / deprecated / acquired / resolved（格式：主值（補充說明））
**領域：** 🤖 模型 / 🛠️ 工具/功能 / 👤 人物 / 💼 商業 / 🏛️ 政策/安全 / 🌐 社群
**首次出現：** YYYY-MM-DD
**最後更新：** YYYY-MM-DD
**最後新聞更新：** YYYY-MM-DD

## 現況

## 熱度與試用價值（feature 類型且熱度 ≥ 🔥🔥🔥 必填）

| 項目 | 評分 |
|------|------|
| 社群熱度 | 🔥🔥🔥 |
| 試用價值 | ✅ / ⚡ / ⏳ / ❌ |
| 最適合 | 適用場景 |
| 不適合 | 不適用場景 |

> 詳細最新熱度見 [[feature-radar]]

## 使用指南（feature 類型且有具體用法 必填）

## 核心功能
## 相關議題
## 參考來源
## 歷史記錄
```

## topics/ 頁面格式模板 `[加入: 2026-04-25]`

```markdown
# 議題名稱

**狀態：** ongoing / resolved / monitoring
**開始日期：** YYYY-MM-DD
**最後更新：** YYYY-MM-DD
**最後新聞更新：** YYYY-MM-DD

## 摘要
## 技術彙整        ← 技術類 topic 用此名；政策/商業類可改用自訂區塊名（見下方說明）
## 目前結論
## 相關實體
## 時序
```

**技術彙整** 區塊：每次 ingest 後累積，條列技術機制、已知限制、workaround，不重複已有條目。議題解決後移至 entities/ 作為歷史記錄。

**政策 / 商業類 topic 的區塊命名：** `技術彙整` 僅適用於技術議題。政策、政治、商業類 topic 可自訂更貼切的區塊名，例如：
- `## 根本矛盾` + `## 三個戰場`（用於多方角力的政策議題）
- `## 核心爭點`（用於單一政策爭議）
- `## 背景分析`（用於商業策略分析）

命名原則：讓讀者從標題就能理解「這個區塊在回答什麼問題」。

## Wiki 頁面呈現品質標準 `[加入: 2026-05-15]`

### 必須修復（ingest 完成前不得跳過）

| 項目 | 判斷方式 | 修復動作 |
|------|---------|---------|
| **頂部 delta-first callout** | 狀態為 `ongoing` 或 `monitoring` 的 topics/ 頁面，標頭後必須有 `> **最新...** （YYYY-MM-DD）` callout 區塊，說明最新一筆重大事件 | 新增或補寫 callout，格式見下方範例 |
| **摘要 delta-first** | `## 現況`/`## 摘要` 的第一句回答「最近發生什麼」，不是「這個頁面是什麼」 | 改寫第一句為最新事件或狀態變化 |
| **摘要可獨立閱讀** | `## 現況`/`## 摘要` 前 160 字能讓不熟悉背景的讀者理解頁面主題 | 改寫摘要段落 |
| **關鍵資訊前置** | 最重要的事實出現在頁面前 1/3 | 將核心表格或結論移至前段 |
| **熱度表格緊接摘要** | 熱度統計表格緊接在 `## 摘要`/`## 現況` 之後，不可置於末尾 | 移動表格區塊 |
| **無 LLM 專屬指令** | 正文不含「請執行」「下一步」「若日報出現…」等操作語句 | 移至對應的 `.claude/rules/wiki-ingest-*.md` 規則檔或刪除 |
| **無維運術語洩漏** `[加入: 2026-07-28]` | 正文與標頭不含 ingest / lint / 派工等內部維運字眼（如「每次 ingest 更新」「此頁為 lint 專用」「下次 ingest 應…」）——讀者只需要「每日更新」「每週策展」這類節奏描述 | 改寫為讀者語言；「更新頻率」欄位的補充說明照 `**更新頻率：** 🗓️ 週更（每週策展一次；更新日期停留數天屬正常節奏）` 格式書寫 |
| **實體狀態變更全檔案 cross-check** `[加入: 2026-07-01]` | 今日更新涉及實體狀態變更（如管制解除、模型下線、功能升版）時，該實體名稱在同一頁面（含摘要、表格、callout、歷史記錄）與被引用的其他頁面中若有殘留舊狀態敘述 | 對該實體名稱 grep 全檔案，逐一確認並統一為最新狀態，不可只改觸發本次修改的那一行 |
| **現況不被時序侵蝕** `[加入: 2026-07-02]` | `## 現況`/`## 摘要` 內帶日期的事件段落超過 2 段（新事件 prepend 進摘要卻不清舊段，會讓摘要變成第二份時序） | 只保留最新 2 段，其餘移入歷史記錄/時序；若該事件已在歷史記錄則直接刪除，不雙重維護 |
| **表格放結論，細節下沉（全站通用）** `[加入: 2026-08-27]` | 任何表格儲存格超過 **120 字元**散文（量測前先剝掉 markdown 連結 URL；純引用來源格〔標題＋URL＋日期〕豁免）——查證過程、演進脈絡、多來源歧異塞進格子會讓表格失去可掃描性並在網站爆版 | 儲存格只留結論短語＋關鍵數字＋最新日期，細節**完整下沉**到該表格正下方的細節區（錨定表內關鍵詞）——細節區條列本身受 `.claude/rules/wiki-reporter-shared.md`「書寫風格」的 200 字元上限拘束，下沉是換位置，不是換成無上限的傾倒區；下沉是搬位置不是刪除，數字與歸因一個不能少。此規則自 `.claude/rules/wiki-ingest-models.md` G/H 條提升為全站通用（2026-08-27 可讀性掃描：政策/商業/功能頁多表同病）；model-comparison 的欄數上限與自查指令仍見該檔 |

**頂部 delta-first callout 格式：**
```markdown
> **最新[動態/進展/事件]**（YYYY-MM-DD）
> 一到兩句說明最新重大事件，讓冷讀者不需往下看也能理解當前狀態。
```
**callout 寫「發生了什麼」，不寫「收錄決策」**`[加入: 2026-07-28]`：未收錄清單、門檻判定理由（「X 未達中門檻，未收錄」）屬編輯部日誌，寫入 `wiki/log.md` 的 ingest 紀錄，不得出現在 callout 或正文——callout 首句必須是當日新增的內容本身。多條互不相關的事件改用 `> - **主題**：一句話` 條列，不擠成單一長段。
callout 放在標頭欄位（最後更新、最後新聞更新）之後，`---` 分隔線之前。entities/ 頁面同樣建議加，但非強制。
**只保留單一最新一則 callout：更新時直接覆寫舊 callout，不得保留「前次動態」等舊 callout 疊加**（callout 是全 wiki 唯一該「覆寫」而非「prepend」的地方；歷史沿革一律進 `## 時序`，不在頂部堆疊）。

### 頁面拆分原則 `[加入: 2026-07-04，改版: 2026-09-03]`

**一頁一故事**：頁面邊界由主題完整性決定，不由行數決定。厚度（> 600 行）只是進入評估的**鬧鐘**，不是拆分理由。拆分只有兩種合法理由：**(a) 子故事**——一個故事裡長出了自己一個故事；**(b) 死案歸檔**——已 resolved 且不再被任何活躍敘事引用的整段。兩者皆須經使用者確認才可執行。

**先跑蒸餾，再談拆分**：厚頁若有 ≥3 個月前的事件流時段，先走本檔下方「時段蒸餾與封存（全站通用）」——2026-09-03 量測：patterns 1,786 行中 1,087 行是早該蒸餾的舊月份，蒸餾後大概率掉到鬧鐘以下，根本進不了三題。

#### 子故事三題（唯一切分判準，三題全過才成頁）

1. **有自己的問題**：讀者會單獨問這個問題來（「提示注入怎麼防」會；「2026-06 發生了什麼」不會——按月切出來的是 log 不是故事）
2. **有自己的結論與時序**：能寫出自己的 delta-first callout、目前結論、事件流，不是借母頁的
3. **被獨立引用**：別的頁 wikilink 進來時指的是這一段（頁級入邊全指整頁的，照精神判：會被單獨引用嗎）

答不齊 → 那只是母故事的一章，該做的是蒸餾（熬濃），不是拆。

#### 階層的語意與紀律 `[加入: 2026-09-03]`

- **parent＝「是它的一部分」（part-of）**，不是「衍生自它」——衍生／引用仍是 wikilink（`community-large-codebase-workflow` 縫合 patterns 的主線，是引用不是子頁）。判斷式：把子頁內容搬回母頁自然嗎？自然 → part-of；不自然 → 引用
- **單一 parent（樹）、規則每層遞迴適用、無深度上限**（使用者裁決）：孫子故事要成頁一樣過三題；深度由故事結構決定
- **階層的單一來源**是子頁標頭一行 `**上層：** [[topics/xxx]]`（放在「領域」之後）；frontmatter `parent`／`children`／`page_role` 由 `scripts/gen_wiki_frontmatter.py` 生成，不手填。**不重用 `kind` 欄**（它是 entity|topic，Bases 視圖在用）
- **子頁扁平放在 entities/ 或 topics/**，slug 自由命名、不編碼階層（日後可改嫁、可升格）；**子頁領域＝母頁領域**（懸置命中靠頁面領域派記者）
- **子頁不入 index 目錄表、不在網站列表平鋪**——只從母頁下鑽（母頁詳頁列子頁卡、子頁有麵包屑；搜尋仍找得到）。index 上母頁列的摘要格由腳本投影一段 `↳ 子故事：[[a]]、[[b]]`（機器投影，家在各子頁的上層欄）——查詢入口與記者認領靠它，記者認領規則「領域＝X 的所有頁面」因此不必改字
- **archive 頁掛在它封存的頁底下**（`**上層：**`），不參與三題、不入 index

#### 母頁契約：升格後母頁必須仍是故事 `[加入: 2026-09-03]`

hierarchy 最自然的衰退是母頁退化成目錄——那正是本原則要避免的東西，所以有機械看守：

| 時點 | 母頁准動什麼 | 誰 |
|---|---|---|
| 每日 ingest | **唯讀**，除三樣：頂部 callout（覆寫）、分支目錄表、既有懸置標記加 `訊` | 記者 |
| 每週 lint | **結論層整線重寫**（照 `community-large-codebase-workflow` 契約：固定分層、行數硬上限、只寫「哪條子故事的答案變了」、不 append、引子頁 wikilink 不複製數字） | 對應類別記者，觸發邊登記在該類 `*-lint.md` |

- 母頁自身「最後新聞更新」**不因子頁動**（動了會與 `check_wiki_freshness.py` 第 2 類互斥、擋 web build）；「母不落後子」改驗 **callout 日期 ≥ 子樹最新新聞**（`scripts/check_hierarchy.py`，掛 `run_tests.py`）；列表排序與訊號用子樹聚合值（frontmatter `days_since_news_subtree`）
- **路由**：母頁對應規則檔的路由表寫明每個子頁收什麼；判不出的節點寫進母頁「未歸類」節（不是預設子頁——那會變雜物間），週更時分派

#### 對稱規則：併回 `[加入: 2026-09-03]`

子頁 < 80 行且 60 天無新聞更新 → lint 提案併回直接上層（需使用者裁決）。併回**必留 redirect 殼**：原 slug 保留標頭＋一行「已併回 [[母頁]]」（`page_role=redirect`），否則週報與外部連結永久斷。

#### 升格／併回 verify 流程（強制）`[加入: 2026-09-03]`

| 階段 | 做什麼 | 機械證據 |
|---|---|---|
| **0 前置** | 厚頁先跑蒸餾；量出蒸餾後行數；仍 > 600 才進三題 | lint 回報行數 |
| **1 盤點 dry run** | 記者對候選頁列子故事，每個附三題答案（引用方頁名＋行號） | 回報表；使用者裁決 |
| **2 手術（同一 commit）** | 建子頁（標頭：領域＝母頁、`上層`）、母頁改寫（callout／目錄／結論層）、回掃 `[[頁#段]]` 錨點連結、懸置標記 `⟨Q-nn⟩` 與細節區成對搬、轉知帳本 `page` 改派、路由規則加子頁 | `python scripts/gen_wiki_frontmatter.py`（產 index 投影）→ `python scripts/run_tests.py` 全綠（含 check_hierarchy／freshness／index_sync／pending_markers／check_tools_page）→ `python scripts/build_web.py` 錨點 WARN 不增 |
| **3 帳本同步** | `python scripts/devpractice_diff.py mark`（搬家 diff 不得被當新料）；log 記升格 | 基準線 sha |
| **4 上站** | 同一 commit push（雲端班次是 fresh clone，配套晚一個 commit 就停站一天） | gate_web_build 綠 |
| **5 冷讀者驗收** | 派冷讀者從 index 走 2 題（1 題母頁層級、1 題子故事層級），3 跳內拿到答案 | 回報 |
| **6 一週回訪** | 下次 lint：母頁 callout 是否跟上、子頁歸因是否落地、`page_role`／訊號是否合理 | check_hierarchy 綠＋lint 回報 |

判斷式：**這次升格，機器抓得到它壞掉嗎？** 答不出 → 還沒到動刀的時候。

### 時段蒸餾與封存（全站通用）`[加入: 2026-09-04]`

蒸餾契約**住這一檔**（頁面格式與階層的家），六類記者共用；`.claude/rules/wiki-ingest-community-lint.md`「月度蒸餾與細節封存」只留社群兩頁的特有判準並指回本節。理由：原契約寫在社群 lint 檔裡，於是 `ai-agent-safety`（1,257 行）、`anthropic-government-policy`（705 行）、`competitor-landscape`（663 行）、`anthropic-business`、`claude-code`、`pricing`、各人物頁的歷史記錄**結構上沒有封存路徑**——不是誰疏忽，是契約住在一個只有社群記者會讀的檔案裡。條文複製到六份規則檔必然漂移，所以通用部分只留一份。

**對象（判準，不窮舉標題）：** 頁面中「依日期堆疊、新的加在上面」的區塊——`## 時序`、`## 歷史記錄`、`## 事件記錄`、`## 攻防紀錄`、以 `### YYYY-MM` 或 `### YYYY-MM-DD` 分組的技術彙整皆屬之。判斷式：**這個區塊的條目是按時間 prepend 的嗎？** 是 → 適用。結論層（摘要、現況、決策表、對照表、風險表）永遠不適用——它們該被覆寫，不該被封存。

**時段 ＝ 一個區塊 × 一個月份**（如 `topics/competitor-landscape` 的 `## 時序` × `2026-04`）。候選門檻：該月距今 **≥ 3 個月**（月份算術：本月序 − 該月序 ≥ 3）。

**三條例外（滿足其一即不蒸）：**
1. **有錨點邊指入**——`python scripts/wiki_graph.py explain <頁slug> --section "<段名>"` 列出的入邊非空
2. **該時段是唯一細節出處**——頂部 callout 或 `## 摘要`／`## 現況`／未結案風險表所述的事實，只在該時段條目裡寫著（同頁他處已有細節家者不算）
3. **狀態 🌊延燒／🌋重燃的討論**，其歷史時段一律不蒸（重燃需要上下文在場）

**產物兩件：**
- 主頁該時段 → **≤ 15 行時段總結**：收斂結論、仍具引用價值的專有名詞、末行固定 `原始條目見 [[<archive 頁>#YYYY-MM]]`（錨點建置會驗）。總結受 `.claude/rules/wiki-reporter-shared.md`「書寫風格」硬上限拘束
- 原文**一字不刪**照搬 append 至 archive 子頁的 `## YYYY-MM` 分組

**archive 子頁（每個母頁一個，slug ＝ `<母頁 slug>-archive`）：** 首次建立時——標頭領域＝母頁、`**上層：** [[母頁]]`、狀態 `resolved（封存頁）`、頂部一句 callout 說明「本頁為原始條目封存，重點層見主頁」；**不補 index 列**，跑 `python scripts/gen_wiki_frontmatter.py` 會投影進母頁列的「↳ 子故事：」（`scripts/check_hierarchy.py` 驗上層、領域繼承、投影、`resolved（封存頁）` 狀態）。既有 archive 頁沿用其既有分節，新時段一律開 `## YYYY-MM`。懸置標記 `⟨Q-nn⟩` 與其細節區條目**成對搬**，不可只搬一半。

**引用回掃：** grep 全庫指向被搬條目的 `[[頁#條目標題]]`，改指 archive 對應錨點（`scripts/build_web.py` 的 `check_wikilink_anchors()` 會驗）。蒸餾是搬位置＋熬濃，不是刪除，斷鏈即違規。

**節奏與角色：** 每次 `/wiki-lint`，各記者對自己負責頁面提案（回報欄 `蒸餾候選：`，格式見 `.claude/commands/wiki-lint.md` 步驟 2 的 3h），主編彙整後**經使用者確認才執行**；**每頁至多 2 個最舊時段**（漸進，不一次大搬家）。無達標時段 → 回報「無蒸餾候選」。

**欄位：** 主頁與 archive 頁都只更新「最後更新」，**不動「最後新聞更新」**——搬位置不是新聞。

判斷式：**這個時段的條目，還有活躍敘事在指它嗎？** 沒有 → 它該進證據層，讓重點層讀得動。

## 懸置標記語法 `[加入: 2026-08-09]`

事實尚未確定時（待查證／待核實／官方未載），**必須用本節語法標記**，不可只寫一句「待查證」了事。

理由：散文裡的「待查證」沒有任何機制讀得到它。2026-08-08 跨 session 訊息互通條目標了「未經官方確認」並寫著「後續 ingest 若查得官方一手來源應更新」——那句話沒有任何流程會去讀，條目掛到使用者親自問起才被發現，而官方文件從第一天就存在。本語法讓每筆懸置**自帶偵測條件**：每日掃描拿探針比對當日日報，命中就通知對應記者。

### 標準式（散文／條列／callout／短表格儲存格）

```
❓ **待查證**（標 2026-08-07｜查 [[topics/ai-agent-safety]]、CI workflow secrets）｜**GitHub Issue 觸及 CI secrets**（2026-08-07 報導）：The Hacker News 報導…
```

四段：`狀態符號` + `**類別詞**` + `（metadata）` + `｜**題目**：內文`。前三段是機器區、第四段是人類區，以全形 `｜` 分界。**括號寫在粗體外**，讓表格處理函式不會動到 metadata。

| 欄位 | 語法 | 必填 | 語意 |
|------|------|------|------|
| 狀態符號 | `❓` / `🔎` | ✅ | `❓` 尚無人查；`🔎` 已查官方一手來源、確認未載 |
| 類別詞 | `待查證` / `查無官方` | ✅ | 與符號一一對應，不一致會被檢查擋下 |
| 標記日 | `標 YYYY-MM-DD` | ✅ | **寫下這個標記的那天，不是事件發生日**。事件日寫在題目後的散文括號裡 |
| 探針 | `查 A、B` | ✅ | 每日掃描拿來比對日報的關鍵字，頓號分隔。`[[wikilink]]` 優先 |
| 複查日 | `複 YYYY-MM-DD` | ⬜ | **省略即為標記日 + 14 天**。有寫代表有人動過手 |
| 訊號日 | `訊 YYYY-MM-DD` | ⬜ | 日報出現後續的那天。**記者唯一可新增的欄位** |

### 表格變體

儲存格加上完整標記後 **≤ 120 字元**（同 `.claude/rules/wiki-ingest-models.md` G 條）就直接用標準式；超過則儲存格只留短標記，完整標記下沉到該表格正下方的「懸置細節」區：

```markdown
| … | ❓ 待查證 ⟨Q-07⟩ |

**懸置細節**
- ⟨Q-07⟩ ❓ **待查證**（標 2026-08-07｜查 [[topics/ai-agent-safety]]、CI secrets）：僅標題可用，攻擊鏈與是否已修補均未見報導
```

`⟨Q-nn⟩` 的 nn 為該頁內序號（不跨頁唯一）。儲存格短標記與細節區定義**必須一一對應**，缺任一邊都會被檢查擋下——這是防止下沉後細節區被順手刪掉的唯一機制。

### 探針怎麼寫

探針決定這筆懸置能不能被偵測到，**寫壞了等於沒標**：

- **能在 `news/*.md` grep 到的字串**：產品名、issue 編號、版本號、機構名、英文術語。不可是形容詞
- **至少 2 個**（掃描要求 ≥2 個同時命中才算，單探針偵測力不足）。唯一例外是 wikilink 探針或長度 ≥ 6 字元的字串
- **長度地板**：英數 ≥ 4 字元、中文 ≥ 3 字元
- **禁用過寬詞**：`Claude`、`Anthropic`、`AI`、`Code`、`API`、`agent`、`model`、`Opus`、`Sonnet`、`Cowork` 這類天天出現的詞，以及 `Reddit`、`GitHub`、`Hacker News`、`ClaudeCode`、`Show HN`、`dev.to`、`lobsters`、`Google News` 這類每則條目必帶的平台/來源名，會每日命中、把真訊號淹掉
- **`[[wikilink]]` 優先**：指向實體頁時探針詞自動取自該頁（改名時跟著更新），且建置會驗證目標存在。**樞紐頁（`claude-code`、`ai-agent-safety` 這類高頻詞頁）的 wikilink 不具偵測力，僅作語意連結**——展開出的別名（slug、H1 標題）本身就是通用詞，會落在上述禁用過寬詞清單，不參與比對；偵測力須靠另外 ≥2 個具體探針撐起（2026-08-10 教訓：`[[entities/claude-code]]` 單獨一個探針曾讓任何標題含「Claude Code」的條目都誤判命中）

### 誰可以動這個標記

| 角色 | 可做 | 不可做 |
|------|------|--------|
| 記者（每日 ingest／lint 3g） | 加 `訊 YYYY-MM-DD`、更新題目後的內文 | **不可刪標記、不可改狀態符號、不可宣告結案**——記者無 web 工具，判準只有日報 |
| 主編（`/wiki-lint` 5c） | 查官方一手來源後三選一：改寫為事實並移除標記／改 `🔎 查無官方`／議題失效則移除；**查實後必須拿探針字串回掃全庫，把仍在說「待查證／推算值」的引用方一併上修**（5c 第 5 步）| — |

> 記者只掃了日報，就只能宣稱日報沒有。**不得寫「至今無後續」**——那讀起來像已經確認過，但答案可能一直躺在官方說明中心（2026-08-08 教訓：pricing 旗艦計費分界懸置 20 天，每天誠實回報「至今無後續」20 次）。

## 大型檔案讀取策略

頁面 > 300 行時，避免一次全讀：
1. 先用 Grep 搜尋目標區塊標題，取得行號範圍

## 命名與分類規則 `[加入: 2026-06-11]`

**entities 狀態**主值限定五項（格式：`主值（補充說明）`）：`active` / `beta` / `deprecated` / `acquired` / `resolved`。**topics 狀態**維持：`ongoing / monitoring / resolved`。

**領域欄位**：所有 entities/ 與 topics/ 頁面標頭必填 `**領域：**`，六選一：🤖 模型 / 🛠️ 工具/功能 / 👤 人物 / 💼 商業 / 🏛️ 政策/安全 / 🌐 社群。`wiki/index.md` 對應欄位須同步。

**新 topics slug 命名規約**（既有頁面不溯及）：社群類 `community-*`、企業類 `enterprise-*`、Anthropic 官方 `anthropic-*`、安全政策 `safety-*`。

**別名欄位（選填）`[加入: 2026-08-28]`**：頁面主題有常用英文名／舊名／媒體慣用別稱，且與中文頁名或 slug 字面不同者，在標頭「領域」之後加一行 `**別名：** Fable 5, Mythos-class`（逗號分隔，只列真實出現過的稱呼，不預測性堆詞）。用途：全庫 grep 與 `scripts/wiki_graph.py sections` 查詢時可命中、記者判斷條目歸屬時對照、未來語意檢索的正名依據——terminology drift（同物多名造成搜尋與連結失準）是 LLM wiki 的已知失效模式，canonical name＋別名是標準解。人物頁英文名、產品頁官方英文名為典型適用；slug 已含該英文者不必重複。

**更新頻率欄位（選填）`[加入: 2026-07-16，改版: 2026-07-28]`**：非每日維護的頁面（週更／lint 專用）在標頭「領域」之後加一行 `**更新頻率：** 🗓️ 週更（讀者導向的節奏說明）`，並在 `wiki/index.md` 對應摘要前綴「🗓️ 週更」——向讀者說明日期停留是設計而非漏更新。補充說明用讀者語言（如「每週策展一次；更新日期停留數天屬正常節奏」），**不得出現 `/wiki-lint`、ingest 等內部指令名**（此欄位會原樣顯示在網站詳頁標頭）。每日維護頁**不加**此欄。目前適用：`wiki/overview.md`、`wiki/topics/community-pattern-trends.md`、`wiki/topics/community-tech-tools.md`、`wiki/topics/model-task-leaderboard.md`、`wiki/topics/community-large-codebase-workflow.md`；日後新增週更頁時比照。
