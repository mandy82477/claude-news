# Wiki 頁面格式規則

建立新頁面、或需確認格式規範時讀取此檔案。

---

## 決策框架：新建頁面類型

- **具體事物**（模型/工具/人物/產品）有足夠描述 → 當天建 entities/ 頁
- **現象/爭議/趨勢** 且 log.md 顯示昨天也出現 → 建 topics/ 頁
- **現象/爭議/趨勢** 今天首次出現 → 暫記於相關 entities/ 歷史，明天再評估
- **entities＝有專有名詞的具體事物；topics＝多方參與的現象/故事。更新頻率不是分類依據**——entities 也會每日更新

## entities/ 頁面格式模板 `[加入: 2026-04-25]`

功能類型（`類型: feature`）且熱度 ≥ 🔥🔥🔥，必須含 `## 熱度與試用價值` 及 `## 使用指南` 區塊。

```markdown
# 實體名稱

**類型：** model / feature / person / product / policy / event
**狀態：** active / beta / deprecated / acquired / resolved（格式：主值（補充說明））
**領域：** 🤖 模型 / 🛠️ 工具/功能 / 👤 人物 / 💼 商業 / 🏛️ 政策/安全 / 🌐 社群
**首次出現：** YYYY-MM-DD
**最後更新：** YYYY-MM-DD
**最後新聞更新：** YYYY-MM-DD

## 現況

## 熱度與試用價值（feature 類型且熱度 ≥ 🔥🔥🔥 必填）

| 項目 | 評分 |
|------|------|
| 社群熱度 | 🔥🔥🔥 |
| 試用價值 | ✅ / ⚡ / ⏳ / ❌ |
| 最適合 | 適用場景 |
| 不適合 | 不適用場景 |

> 詳細最新熱度見 [[feature-radar]]

## 使用指南（feature 類型且有具體用法 必填）

## 核心功能
## 相關議題
## 參考來源
## 歷史記錄
```

## topics/ 頁面格式模板 `[加入: 2026-04-25]`

```markdown
# 議題名稱

**狀態：** ongoing / resolved / monitoring
**開始日期：** YYYY-MM-DD
**最後更新：** YYYY-MM-DD
**最後新聞更新：** YYYY-MM-DD

## 摘要
## 技術彙整        ← 技術類 topic 用此名；政策/商業類可改用自訂區塊名（見下方說明）
## 目前結論
## 相關實體
## 時序
```

**技術彙整** 區塊：每次 ingest 後累積，條列技術機制、已知限制、workaround，不重複已有條目。議題解決後移至 entities/ 作為歷史記錄。

**政策 / 商業類 topic 的區塊命名：** `技術彙整` 僅適用於技術議題。政策、政治、商業類 topic 可自訂更貼切的區塊名，例如：
- `## 根本矛盾` + `## 三個戰場`（用於多方角力的政策議題）
- `## 核心爭點`（用於單一政策爭議）
- `## 背景分析`（用於商業策略分析）

命名原則：讓讀者從標題就能理解「這個區塊在回答什麼問題」。

## Wiki 頁面呈現品質標準 `[加入: 2026-05-15]`

### 必須修復（ingest 完成前不得跳過）

| 項目 | 判斷方式 | 修復動作 |
|------|---------|---------|
| **頂部 delta-first callout** | 狀態為 `ongoing` 或 `monitoring` 的 topics/ 頁面，標頭後必須有 `> **最新...** （YYYY-MM-DD）` callout 區塊，說明最新一筆重大事件 | 新增或補寫 callout，格式見下方範例 |
| **摘要 delta-first** | `## 現況`/`## 摘要` 的第一句回答「最近發生什麼」，不是「這個頁面是什麼」 | 改寫第一句為最新事件或狀態變化 |
| **摘要可獨立閱讀** | `## 現況`/`## 摘要` 前 160 字能讓不熟悉背景的讀者理解頁面主題 | 改寫摘要段落 |
| **關鍵資訊前置** | 最重要的事實出現在頁面前 1/3 | 將核心表格或結論移至前段 |
| **熱度表格緊接摘要** | 熱度統計表格緊接在 `## 摘要`/`## 現況` 之後，不可置於末尾 | 移動表格區塊 |
| **無 LLM 專屬指令** | 正文不含「請執行」「下一步」「若日報出現…」等操作語句 | 移至對應的 `.claude/rules/wiki-ingest-*.md` 規則檔或刪除 |
| **實體狀態變更全檔案 cross-check** `[加入: 2026-07-01]` | 今日更新涉及實體狀態變更（如管制解除、模型下線、功能升版）時，該實體名稱在同一頁面（含摘要、表格、callout、歷史記錄）與被引用的其他頁面中若有殘留舊狀態敘述 | 對該實體名稱 grep 全檔案，逐一確認並統一為最新狀態，不可只改觸發本次修改的那一行 |
| **現況不被時序侵蝕** `[加入: 2026-07-02]` | `## 現況`/`## 摘要` 內帶日期的事件段落超過 2 段（新事件 prepend 進摘要卻不清舊段，會讓摘要變成第二份時序） | 只保留最新 2 段，其餘移入歷史記錄/時序；若該事件已在歷史記錄則直接刪除，不雙重維護 |

**頂部 delta-first callout 格式：**
```markdown
> **最新[動態/進展/事件]**（YYYY-MM-DD）
> 一到兩句說明最新重大事件，讓冷讀者不需往下看也能理解當前狀態。
```
callout 放在標頭欄位（最後更新、最後新聞更新）之後，`---` 分隔線之前。entities/ 頁面同樣建議加，但非強制。

### 頁面拆分原則 `[加入: 2026-07-04]`

**一頁一故事**：頁面邊界由主題完整性決定，不由行數決定。行數只是「結構檢查觸發器」——超標時檢查頁面有無入口層（delta-first callout、概覽表、月份/主題分組），有入口層即通過，不因為長而拆分。
拆分只有兩種合法理由：**(a) 語意分岔**——一個主題實際長成兩個獨立故事；**(b) 死案歸檔**——已 resolved 且不再被任何活躍敘事引用的整段。兩者皆須經使用者確認才可執行。

### 警示觸發重構（超過閾值時嘗試修復；工作量過大則記錄 log.md 待辦）

| 警示條件 | 閾值 | 重構方向 |
|---------|------|---------|
| 頁面過長 | > 200 行 | 檢查入口層結構（callout / 概覽表 / 月份或主題分組），有入口層即通過；缺入口層才補結構，不建議拆分 |
| 事件流堆積 | 連續 8 個以上 `### YYYY-MM-DD` 無主題分組 | 合併為主題段落 |
| 缺少結構化 | 方案比較以純段落表達 | 改為 Markdown 表格 |
| 表格不可排序 | 欄位值格式不一致 | 統一日期、熱度、狀態符號格式 |
| 摘要缺失 | `## 現況`/`## 摘要` 空白 | 從頁面內容萃取補寫 |
| 指標表凍結 `[加入: 2026-07-02]` | 核心指標/統計表格的數據日期落後「最後新聞更新」超過 21 天 | 更新表格數據；無新數據可更新時在表格上方標註「數據截至 YYYY-MM-DD」，避免讀者誤判新鮮度 |

### ingest 結尾強制輸出

```
| 呈現品質審查 | 每頁：✅ 通過 / ⚠️ 已修復（說明）/ 📋 已記錄待辦（說明問題）|
```

## 大型檔案讀取策略

頁面 > 300 行時，避免一次全讀：
1. 先用 Grep 搜尋目標區塊標題，取得行號範圍
2. 用 `Read` + `offset`/`limit` 只讀取需要的段落
3. 同一次 ingest 中多個無關頁面的更新，在單一訊息中平行發出多個 Edit 呼叫

典型大型頁面：`community-tech-patterns.md`、`community-tech-timeline.md`、`claude-code.md`

## 命名與分類規則 `[加入: 2026-06-11]`

**entities 狀態**主值限定五項（格式：`主值（補充說明）`）：`active` / `beta` / `deprecated` / `acquired` / `resolved`。**topics 狀態**維持：`ongoing / monitoring / resolved`。

**領域欄位**：所有 entities/ 與 topics/ 頁面標頭必填 `**領域：**`，六選一：🤖 模型 / 🛠️ 工具/功能 / 👤 人物 / 💼 商業 / 🏛️ 政策/安全 / 🌐 社群。`wiki/index.md` 對應欄位須同步。

**新 topics slug 命名規約**（既有頁面不溯及）：社群類 `community-*`、企業類 `enterprise-*`、Anthropic 官方 `anthropic-*`、安全政策 `safety-*`。
