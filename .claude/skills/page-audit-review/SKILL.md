# 頁面健檢與重設計 — Mandy 的 review 偏好

來源：CLAUDE_NEWS 2026-09-05 競品頁試點（使用者親自定框架、逐步裁決，全流程與教訓見該專案 `docs/page-audits/competitor-landscape-2026-09-05*.md`）。專案專屬 skill（使用者裁決不做全域）。跨專案通用的 review 底線另見 `C:\Users\Mandy\.claude\REVIEW-PRINCIPLES.md`，派評審 agent 時兩份都要讀。

## 總則（使用者原話，寫進每個 agent 的 prompt）

> **不合規就大膽思考，小心設計。**

- **先問頁面存在的理由，再談版面。** 先修合規／文筆是反的——上一輪先修版面才發現沒問過「這頁要回答誰的什麼問題」。
- **使命句不能太硬。** 「我要不要換」這種逼每列給裁決的使命，資料撐不起就會製造假結論；改問「**會帶來什麼衝擊、多大**」，裁決句只在有硬證據時出現。不虛報優先於行動導向。
- **行動導向仍要有**：每則要有「⏰ 接下來看什麼」「你的選項」這類 action item，列選項不下指令。
- **輸出要短。** 使用者對長文很敏感（「字數好多欸」）：日報級的東西五行內，長版另存連結過去。
- **拆頁是合法選項**，用子故事三題判（有自己的問題／自己的結論與時序／會被獨立引用），不用行數當理由；母頁拆完必須仍是「雷達」不是目錄。
- **模型分工**：冷讀者、設計、評審用 Opus（挑剔度差很多）；機械掃描與搬運用 Sonnet；派工前先報價（幾個 agent、哪一級）。

## 健檢卡：六問（每問附證據：行號、節名、數字）

1. **這頁要回答什麼** ＝ (a) 使用者問過的〔專案 Query 史、reader-notes、**現場口述兩分鐘**〕∪ (b) 設計上追蹤的〔從 index 路由描述、蒐集邊界、維護者規則、入邊語境反推〕→ 合成**考題集**，每題標 a/b。使命句定稿**要使用者確認**才進第 2 問（防自問自答）。
2. **版面達得到嗎**：逐節答「服務哪幾題、是雷達還是百科、留／改／併／砍／下沉／拆」。
3. **重設計丟什麼留什麼**：只在第 2 問不及格才進設計分支（見下）。
4. **與鄰居頁重疊混淆**：每對鄰居一句分工原則＋現況違反處（行號）。機械輸入：圖的入邊／出邊、相似度、缺口偵測。
5. **有熱度的表格有沒有淘汰機制**：先跑表格普查（成長型態 prepend/append/static × 規則檔有無淘汰／覆寫／封存詞），無機制的成長表就是未來爆版點；給每張表「該是覆寫式還是累積式＋判準句」。
6. **精緻度**：最後、最短；只在前五問過了才輪到文筆。

**機械項先行**：第 4、5 問的腳本輸出先跑完當健檢卡輸入，不讓 Opus 邊健檢邊手查。

## 角色分離（最重要的結構）

| 角色 | 做什麼 | 紀律 |
|---|---|---|
| 健檢卡 agent | 六問＋預測每題卡點 | 只診斷，不開藥到細節 |
| 冷讀者 | **獨立 context**，從站的入口（index）實答考題，記路徑／跳數／卡點／引用原句；總評「百科還是雷達」＋三個最想改＋內部用語外洩＋哪兩頁搞混 | 不知道產製流程與內部術語；不可直接開已知檔名 |
| 設計 agent | 2–3 個**有真實差異**的提案（單頁重組／拆頁／最小改動），每案附骨架、核心表格判準與真實示範列、**現有內容逐行號去向（一行不憑空消失）**、鄰居分工落地、**維護者同步**、機械契約、拆頁三題判定、風險 | 可大膽改規則、改流程、移交鄰居頁 |
| 評審 agent | 對抗式，輪流站四個人：**明天的維護者**（規則改了會不會寫回舊形狀）、**機器**（錨點／registry／檢查腳本）、**冷讀者**（逐題預測）、**治理**（有沒有偷偷立法、去向表對不對、越界改他人檔）；每條 🔴🟡🟢 附可貼上的修法 | 沒有解法的 🔴 不是評審是抱怨 |
| ~~設計 agent 第二輪~~ → 主 session 照評審清單改 `[改版: 2026-09-05]` | 本環境無子 agent 續用（`SendMessage` 不存在），重派設計者等於全量重讀一次（第 1 波實測 28.5 萬 token）。改為：評審者的修法即定稿，主 session（或一位 Sonnet）照「照順序執行」清單改；裁決點由主 session 收斂到 **≤3** 端給使用者。設計者只派一次且交件前先自己過閘——契約逐字見 `docs/page-audits/dispatch-prefix.md`「設計者／評審者／交棒數預算」 | 若日後 `ListAgents` 列得出子 agent，本列改回續用版 |
| 使用者 | 裁決 | — |
| 實作 agent | 照定稿做，**維護者同步同一 commit**（版面改、規則跟）；跨維護者的內容走交辦帳本不直接寫他人頁；兩刀（規則＋前置手術 → 版面） | 偏離定稿要明列理由 |
| 冷讀者（複驗） | 拿**原考題集**再考一次，前後可比；一週後回訪看每日更新有沒有把版面磨回去 | 同上 |

健檢卡的預測卡點 vs 冷讀者實測要對照——對得上才代表健檢卡可信。

## 評審常抓到的病（試點實例，寫進評審 prompt 當檢查清單）

- 設計 agent 的示範列違反自己寫的判準（衝擊度與證據硬度量成同一根軸）。
- 蒸餾／封存門檻算錯月份、超過每次上限、把非時序區塊塞進封存。
- 宣稱「lint 會看守」但腳本裡沒有那個邏輯——**去讀原始碼驗證**。
- 叫維護者（記者）去改它無權改的檔（index）。
- 懸置／待辦標記短標記與定義區拆對——而且舊格式對機器隱形，拆了是**靜默壞掉**比報錯更糟。
- 「事實跑錯家」的內容（屬別頁／別的維護者），三案都沒走交辦帳本。
- 把不會被任何 script 消費的判準塞進契約 registry（零看守力）。
- 「先做最小改動當第一刀」——第一刀立的規則下週被第二刀推翻，等於先立一版要廢的規則；直接做定稿。
