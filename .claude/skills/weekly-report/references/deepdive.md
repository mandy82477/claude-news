# 第 (2) 段：技術討論＋深挖

`.claude/skills/weekly-report/SKILL.md` 步驟 4 第 (2) 段的規則單一來源。括號內的「反例／實據」是界標，全文敘述見沿革檔 `docs/rules-changelog/weekly-report.md`。

- 開頭固定 **2–3 行「本週版本」**：升版 go/no-go＋breaking change 提醒（無大事一行帶過）
- **討論綜述**：本週社群在吵什麼、測什麼（廣度，**半頁上限**；每條給冷讀者一句話脈絡）
  - **研究、指南、工具、稽核這幾類條目，必須帶一句「可以直接用的一件事」**（具體到讀者能照做：開工第一句講什麼、description 要檢查哪兩點）。「暫無動作可做」只留給真的無事可做的治理與政策新聞——整節若超過一半是「暫無動作」，代表選材偏到新聞摘要去了，回頭換條目。來源若有利害關係（賣工具的人出的報告）當句講明。
- **深挖專欄**（獨立小標 `### 深挖：主題名稱`，**900–1,300 字，只算讀者讀得到的字**）：教學式深挖——前 1/3 基礎快講（照顧冷讀者），後 2/3 進階深挖（機制、帳目、坑）

  > ⚠️ 小標是 **`###`**——它是輸出檔 `## 二、技術討論與深挖` 的子標題，與同層的「本週版本」「討論綜述」齊平。**不要照抄本規格檔自己的標題深度**（本檔在這裡是 `##`，輸出檔少一層）。
  >
 > 字數 **900–1,300**、且**只數可見字**（剝 URL／wikilink 路徑／反引號／粗體星號，`deepdive_visible_len()`）；兩項均由 `scripts/check_weekly_ledger.py` 機械檢查（提醒，不擋）。超標時**該拆的是內容不是尺**——不得為讓當期通過而調高上限。（三次校準的實測數列見沿革檔 2026-08-30 A）

**通則四修（防綁死／防雜燴／防假教學／防重複）：**

| 修 | 規則 |
|---|---|
| a. 防綁死 | 題目**優先**從討論綜述選，但可從當週任何技術材料選（版本、官方公告、獨立文章） |
| b. 防雜燴 | 深挖必須有獨立小標與字數框，結構上看得出「專欄從這裡開始」 |
| c. 防假教學 | 先過下方「讀者下週一用得上嗎」，再要求深挖帶一層**機制解釋**（讀者學完能說出為什麼有效、什麼時候不適用）——機制是用來撐住那個做法的，**不是入選門檻**。兩者都達不到 → 本週省略，不硬寫 |
| d. 防重複 | 對照步驟 3 的已深挖題目清單；重複題必須有新角度才准再上 |

## 先過這一關：讀者下週一用得上嗎

**深挖與綜述的第一個問題不是「這題有沒有機制可講」，是「讀完的人下週一會不會做一件不一樣的事」。** 機制層是手段，不是門檻——它的用途是讓讀者知道那件事為什麼有效、什麼時候不適用。

> 為什麼要寫下這條（2026-09-20 使用者回饋：「選材範圍太少，寫出來的東西好像沒有直接幫助」）：原本的入選判準是「教得出機制層」＋「本週有訊號」，兩條合起來會**系統性偏好資安事故與計費爭議**——那兩類天生帶機制與數字；而「新功能怎麼用好」「官方量出來的做法」「社群實測過的設定」這些最能直接套用的東西，反而因為「沒有事故」被擋在外面。九期深挖的實際分佈：成本／用量 5 期、安全 2–3 期、規則寫法 2 期，**新功能怎麼用、選型、工作流 0 期**。W38 初版選了 Plugin4Shell：機制漂亮，但修補三個月前就出貨了，幾乎每個讀者跑 `claude --version` 都直接過關，沒有事要做。

**選材池要撈這五種，不是只撈事故：**

| 來源 | 例 | 讀者拿到什麼 |
|---|---|---|
| 新出貨的功能與行為變更 | AGENTS.md 支援、Auto mode 分類器改伺服器端 | 要不要改設定、哪些情況不適用 |
| 官方文件異動 | 日報「官方文件更新」條目 | 官方悄悄改了什麼規則 |
| 官方研究與指南 | 40 萬 session 研究、使用最佳實踐 | 量出來有效的做法 |
| 社群量測過的做法與稽核 | 216 個 skill 稽核、成本實測 | 拿來對照自己的設定 |
| 事故與爭議 | 資安揭露、計費爭議 | 該不該擋、該不該關 |

**題材輪替**：深挖連續兩期落在同一群（成本／安全／規則寫法／新功能用法／選型與工作流）→ 第三期換群，除非當週該群有頭條級事件。

## 選題三判準

題目**由本週討論熱度決定，不由本週素材密度決定**。三條全過才寫：

1. **本週有訊號**——日報或討論綜述至少一則相關條目，且開頭一句要說得出「為什麼是這週」。沒有本週訊號 → 那是常設教學，屬 `wiki/topics/coding-workflow-guide`，不是週報深挖
2. **寫得出「寫作方向三件套」**（見下）——寫不出來代表這題還沒想清楚，**此刻換題，而不是寫到一半才發現**
3. **每個機制斷言可指回可取回的來源**（見「來源紀律」）

**對興趣主題要比對意思，不是比對字面。** 選題前對 `wiki/reader-notes.md` 每一條 ⏳ 🔍 各寫一行：「本週哪個事件算它的訊號？／無」。不寫這一行，優先權就形同虛設——九期只有 W35 命中過一次，而 W37（GPT 對照，當週日報提及 12 次）與 W38（AGENTS.md 出貨——它本身就是一份跨工具的**格式規約**，正是「codebase map／agent 記憶格式規約」那條在等的第三個節點，當週提及 8 次）都有訊號卻沒對上，因為讀的是筆記的字面（「codebase map」）而不是它要的東西（「format 怎麼定義」）。寫進完成回報，讓漏對看得見。

**優先序：本週熱點 × 讀者興趣。** 同時有多題過三判準時，**命中 `wiki/reader-notes.md` ⏳ 🔍 興趣主題者優先**——那代表讀者主動問過、而庫內覆蓋不足，是需求面已被證實的題目，比單純熱度高的題目值得寫。命中時在深挖開頭的「為什麼是這週」一句裡帶出這層（例：「這題你問過，本週剛好有官方文件可以回答」），並在檔尾素材說明（即檔尾 **素材涵蓋窗** 段）註明命中哪一條。

> 深挖寫完若解掉了某條 🔍，回報中提醒使用者可將該筆標 ✅（本 skill 不自行改 `reader-notes.md` 狀態，避免與 `/wiki-weekly-review` 的消費權責重疊）。（教訓見沿革檔 2026-08-20）

## 寫作方向三件套（動手前必須先寫出來）

| 項目 | 要求 |
|---|---|
| **一句讀者動作** | 讀完會改變的**具體**事，必須指名對象：旗標／檔案／指令／數值門檻／決策規則。只答得出「他會更了解這件事怎麼運作」→ 那是評論不是深挖，換題 |
| **四段大綱** | 基礎快講要講什麼、機制層要解釋哪一個「為什麼」、有幾個陷阱、怎麼用收在哪句判斷 |
| **缺口清單** | 四段裡哪幾格現在沒有素材——這是外查的**目標清單**，讓查找有方向而不是漫無目的補料 |

## 來源紀律

不限來源位置，只有一條：

> **機制層的每個斷言都要能指回一個可取回的來源**（URL ＋ 取得日期），並在正文標明。
> 唯一豁免是**從已標來源的事實推導出的結論**，但推導過程要看得見，且結論標「（推論）」。
> 兩者皆非 → 那是撰稿者的通用工程知識，**刪掉**。

**來源要可點**：官方文件、公告、報導一律用行內 markdown 連結（W35 全篇零連結是退步）；`[[wiki 頁]]` 指路對外部讀者點不開，指路句必須同時給**一句 ≤40 字的結論摘要**（含關鍵數字或狀態詞，讀者不點那頁也拿得到答案）。**「見下方 X」的 X 必須真的存在於本期週報**——寫指路句前先確認目標段落已寫出。（反例：W35 承諾換算表而表不存在）

有缺口就去查（WebFetch／WebSearch），不要因為素材不足而降格題目或灌水撐字數。

> ⚠️ **無 egress 環境的退路**：外查依賴網路。本 skill 目前只在本機執行（`/weekly` 無雲端排程，見 SKILL.md 步驟 6），故不受影響；**若日後上了雲端排程，該環境 egress 封鎖、外查步驟不可用**，該期必須改寫素材自足的備援題，並在檔尾註明「本期於無外查環境產出」，不得靜默地少查。

## 寫作風格（依 W30–W32 實測歸納，W33 為反例）

**四段骨架，每段帶粗體功能標籤**（讀者要能跳讀）：

```
**基礎快講**          定義 ＋ 與相鄰概念的區分          ~15%
**機制層**            為什麼會這樣（一層新的解釋）      ~20%
**N 個陷阱**          編號，每條獨立                    ~45%  ← 價值密度最高，不可省略
**怎麼用**            一句 if/then 決策規則             ~20%
```

**六條寫作規則：**

1. **每個斷言帶具名可驗證物**——參數名、預設值、錯誤碼、版本號、檔名、指令。（正例：W30 的 `effort` 值域、預設 `high`、400 錯誤、`max_tokens` 起調點）
2. **用對比定義新概念**，不用定義句。冷讀者靠差異建座標比靠定義快（正例：W30「`thinking` 控制要不要思考，`effort` 控制整個回應花多少 token」）
3. **第二人稱＋操作現場**（正例：W32「你在終端機打 `claude` 之後、還沒輸入任何東西之前」）
4. **陷阱編號且各自獨立**，每條＝為什麼會出錯 ＋ 正確做法，不合成散文
 - **標題寫成讀者看得懂的中文**：「會咬人的 N 件事」是英文慣用語直譯，中文讀不出「陷阱」那層意思。改用「N 個陷阱」，或就這一篇的內容寫具體（如「三個會讓你算錯的地方」）；**其他英文慣用語直譯同理**——判斷式：把這個詞念給沒讀過英文原文的人聽，他猜得出意思嗎？
5. **結尾是決策規則，不是總結**（正例：W30 收在「先在 effort 這條軸找到工作點，再考慮是不是真要換模型」）
6. **邊界說明內嵌在證據旁**，禁止獨佔結尾段——誠實要散在正文裡，不是堆成免責聲明

**三條禁止：**

- ❌ 同一句話換說法重講（反例：W33 同一句講四次）
- ❌ 沒有具名物的形容詞（「效能不錯」「有落差」）；量不到就不寫
- ❌ 以免責聲明收尾（讀者最後印象會變成全篇不可信）

> 刻意不規定的：語氣詞彙、句長、比喻用不用——不可檢查的規則寫進規格只會變成裝飾。

## 讀者版禁用內部詞

**射程**：本表只管**散文與結果欄的敘述文字**。以下三處不受本表拘束、且一個字不可改：兩張表的固定小標、表頭欄名（皆見 `.claude/skills/weekly-report/references/contracts.md`）、**已寫下的**判準欄儲存格（立案寫定即凍結，回收時逐字沿用，不得為套用本表回頭改字；**新立**判準仍須守「判準形狀」的讀者語言要求）——它們是三支程式的機械契約（`scripts/build_web.py`／`scripts/check_weekly_ledger.py`／`scripts/scan_open_forecasts.py`），不是讀者內容。

以下詞彙屬產製流程語言，**不得出現在週報正文**（冷讀者實測「像不小心看到後台」）；要表達對應概念用右欄讀者語言：

| 禁用 | 改寫 |
|---|---|
| 「判準第 N 支」「逐字凍結」「機械比對」 | 不寫——結果欄直接講結論，程序性交代退到句尾括號也不得用這些詞（表頭欄名「判準」不在此限，見射程） |
| 「長期警示」（未定義的內部分級） | 首次出現時定義，或改寫「已轉入 [[頁]] 長期追蹤（本刊不再逐週報告）」＋一句該頁現在說什麼 |
| 「選材」「pipeline 產出」「本指令」「帳本」 | 改讀者語言；「本指令不自行改…」這類話寫進回報，不寫進週報。**例外：檔尾必須是全檔最後一段，形狀見 `.claude/skills/weekly-report/references/contracts.md`（分隔線＋標籤＋檔案結尾三者，缺一則檔尾整段不上站並污染 stats）**，標籤後的說明文字才用讀者語言（「本期取材自 MM-DD ~ MM-DD 的每日新聞」）|
| 「額度取常態值」等未定義簡稱 | 寫全（「新開條數上限取 3–6 的中間值」）或不寫 |

判斷式：把這個詞念給沒讀過本專案規則檔的訂閱者聽，他猜得出意思嗎？猜不出就不上正文。
