# Wiki 可讀性掃描

不定期執行（建議每 2–4 週，或大量 ingest 後）。與 `.claude/commands/wiki-lint.md` 的分工：lint 檢查結構正確性（矛盾、孤立、格式標準），本指令只看**讀者視角的可讀性**，且刻意用最省 token 的取樣方式。

---

## 執行方式：Spawn 單一背景 Agent

用 **Agent tool**（`run_in_background: true`）派**一個** agent，不派六記者——可讀性問題九成暴露在頁面開頭與結構層，單一視角掃全站反而更容易發現跨頁共通毛病。

**Agent prompt（`{TODAY}` 替換為今日日期）：**

```
你是 wiki 可讀性審查員。工作目錄：C:\Users\Mandy\CLAUDE_OBSIDIAN\ObsidianLab\CLAUDE_NEWS

任務：以最省 token 的方式審查 `wiki/entities/` 與 `wiki/topics/` 全部頁面的**可讀性**（不是內容正確性），只回報不修改。

**省 token 鐵則（嚴格遵守）：**
- 先用一次 `wc -l wiki/entities/*.md wiki/topics/*.md` 拿到全部行數
- 每頁只允許：Read 開頭 60 行 + grep -n "^## \|^### " 看標題結構
- **禁止全文閱讀任何頁面**

**每頁依五項評分（讀者視角）：**
1. 冷讀者測試：callout + 摘要前 160 字，不懂背景的工程師能否知道「這頁在講什麼、最新狀態是什麼」？
2. 掃描性：標題能否讓人不讀內文就知道每區塊回答什麼問題？關鍵結論是否在前 1/3？
3. 長度負擔：頁面長但開頭有概覽表/callout 可跳讀＝可接受；長且無入口＝❌
4. 格式一致性：開頭 60 行內的日期格式、狀態符號、表格欄位是否一致
5. 視覺節奏：開頭是否連續大段純文字牆（超過 8 行無表格/列表/分隔）

**評分：** ✅ 好讀 / ⚠️ 有具體可改進點 / ❌ 冷讀者會迷路

**輸出格式（最終訊息就是報告，不要敘述過程）：**

## Wiki 可讀性掃描報告（{TODAY}）

### 總覽
| 頁面 | 行數 | 評分 | 主要問題（一句）|
（全部頁面，依 ❌ → ⚠️ → ✅ 排序）

### 最需要處理的 5 頁
每頁：問題具體描述 + 建議修法（一兩句，可執行）

### 跨頁共通問題
（多頁犯同樣毛病時歸納成模式）
```

## 收到報告後

1. 把「最需要處理的 5 頁」與共通問題呈現給使用者，**等待確認要修哪些**
2. 依確認結果修復：單頁小修直接改；跨多頁的共通問題可派對應類別記者（見 `.claude/rules/wiki-ingest.md` 派工表）
3. 修復後在 `wiki/log.md` 末尾 append：

```
## YYYY-MM-DD 可讀性掃描

- 掃描頁數：N（✅ X / ⚠️ Y / ❌ Z）
- 已修復：（列出，若無則寫「無」）
- 使用者跳過：（列出，若無則寫「無」）
- 共通問題：（一句歸納 or 無）
```

## 注意事項

- 繁體中文為主
- `log.md` 只能 append；`news/` 唯讀
- 修復頁面時更新「最後更新」欄位（純格式修正不動「最後新聞更新」）
- 本指令產出屬建議性質，**未經使用者確認不執行修改**
