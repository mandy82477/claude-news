# Weekly Report — 週報產生

> **這是週報本體，不是每週的入口。** 平常跑 `/weekly`（總指揮，會依序帶起本指令與 `.claude/commands/wiki-weekly-review.md`）；單獨執行本指令只在補跑或修正單一期週報時使用。
> 單獨執行時，收尾（步驟 6）由本指令自己負責；由 `/weekly` 帶起時，**步驟 6 一律跳過**，收尾交給總指揮統一做（單一 push，理由見該檔）。

「當週技術新聞的教學式深挖」專欄。題目跟新聞走（本週最有料的技術題），寫法是教學的（基礎快講＋進階深挖混合深度），**不是預排課綱**。

**讀者：** 使用者自己＋會分享給別人（冷讀者要能讀懂，基礎概念不可跳過）。
**全文 5 分鐘讀完。**

---

## 使用方式

- `/weekly-report`：產生本週（今日所在 ISO 週）的週報
- `/weekly-report 2026-W30`：指定週次（用於補跑或修正）

平常不直接下這個指令——見檔首說明，每週入口是 `/weekly`。

---

## 步驟

### 1. 決定週次與輸出路徑

取 ISO 週號（若 `$ARGUMENTS` 指定則用指定值，否則用今日所在週），輸出至 `weekly/YYYY-Wnn.md`（`weekly/` 目錄不存在則建立）。

### 2. 蒐集素材

**選題素材**（決定寫什麼）固定涵蓋窗：**近 7 日** `news/*.md`（唯讀，不可修改）＋ `wiki/log.md` 同期 ingest 紀錄＋ `wiki/feature-radar.md`＋ **`wiki/reader-notes.md` 狀態 ⏳ 的 🔍 興趣主題** `[加入: 2026-08-20]`。

**內容素材**（決定深度）不受此窗限制 `[加入: 2026-08-16]`——`wiki/` 既有頁面、任何一期歷史日報、官方文件、以及**依缺口向外查找**的第三方來源皆可用。約束不在來源位置，在來源可取回性，見第 (2) 段「來源紀律」。

> 2026-W33 踩過：把涵蓋窗當成內容來源，於是本週最值得寫的兩題（浮水印、subagent 靜默失敗）都因為「日報只有標題層級」而被排除，剩下唯一素材夠的題目被硬撐到字數下限。**素材窗是用來確保選題貼著本週，不是用來限制能查多深。**

### 3. 檢查已深挖題目清單（防重複）

掃描既有 `weekly/*.md`（若有）的「深挖：」小標題，列出近期已深挖過的題目。本週選題撞到舊題目時，必須有**新角度**（新事實或新機制層）才准再上；否則換題。

### 4. 撰寫四段式結構

#### (1) 頭條敘事

當週最大張力縫成一條因果敘事，**300–500 字，不列清單**。

以下規則依 W30–W34 五期實測歸納 `[加入: 2026-08-25，W35 起生效]`；帶「🔧」者由 `scripts/check_weekly_ledger.py` 對 **2026-W35 起**的期數機械檢查（舊期已凍結，不回溯）。

##### 結構層：為誰寫、線怎麼選、怎麼收

1. **入口讀者裁定**——首段的敘事入口必須是排序最高讀者（Claude Code 重度使用者）**當週實際經歷或可感知的事件**；商業／生態消息可以是本週最大的線，但只能作為第二段以後的「另一側」，不得開篇。例外：當週使用者側無頭條級事件時方可從生態側開篇，並於檔尾涵蓋窗註明。（反例：W33／W34 連兩期從財經媒體視角開篇——素材密度壓過讀者排序，與深挖選題「由討論熱度決定、不由素材密度決定」是同一種病）
2. **編線准入**——收束段必須逐線交代該線在因果鏈中的位置（推動什麼、或被什麼推動）；點不到名、或只能以「同一週也發生了」連接的線 → 整段移出頭條（入討論綜述或本週數字）。**線數由因果鏈決定，不由當週大事數決定**——兩條緊的線優於三條鬆的。（正例：W33 收束「算力合約要營收支撐、營收要收緊用量、合規要產出可辨識」三線各有因果位置；反例：W34 收束只縫營收與配額，浮水印線缺席卻佔頭條一段）
3. **頭條-深挖分工**——同題時頭條只寫意義層（為什麼構成本週張力），機制層數字與官方文件引用只住深挖，且頭條收束段須有一句顯式路由（「……拆開來是什麼，見本期深挖」）；不同題時，頭條懸而未答的問題若本期無解，明寫「列入下週看什麼」並確認預告表真有該列，不得偽裝成有答案。（反例：W34 頭條收尾的「為什麼是我」正是 800 字後深挖拆解的問題，卻零指引）

##### 連載層：跨期連續性

4. **前情錨＋增量**——延續上週的線（同一組行動者＋同一衝突），首句必須同時給：**前情錨**（≤25 字從句，含起點日期＋發生了什麼，服務冷讀者）與**本週增量**（新事實／官方動作／狀態變化，服務連續讀者）。寫不出增量的延續線降入討論綜述；三條線與上期重疊 ≥2 且均無增量 → 換題，或改寫成「張力未解，但 X 動了」的推進式敘事，不得重講。（反例：W34「浮水印的餘波」——餘的是什麼波全篇未交代，起點事件只寫在 W33）
5. **固定稱呼**——每條線指定一個 ≤10 字固定稱呼，首見處以完整敘述定義，其後**全篇（含討論綜述、深挖、下週看什麼、本週數字）逐字沿用**，不得換說法、不得用「那則」「前述」回指；補細節寫成「稱呼＋補述」。（反例：W34 同一起事件六種說法，「排程情境下的模型替換」讀起來像另一個新機制，而它就是同一則）

##### 句子層

6. **收束預算**——對仗判斷句（「不是 X 而是 Y」等）全文 ≤1 次且只能在末段，其餘段落陳述事實不下判斷；末段結論句**禁抽象隱喻**，寫成讀者可直接覆述的因果句。（正例：W33「規模化的三個代價同時到齊」——具體枚舉；反例：W34「是同一種東西的兩端」——要求讀者先自行具體化兩端再對齊）
7. 🔧 **跨期句式防重複**——動筆前 diff 上期頭條末段的句法骨架，同構即換收束方式（時間因果鏈、反問、或直接給結論）。機械檢查擋的是連兩期命中「把 N 條線並排」句型。（實據：W33「把三條線並排看，這週的故事不是…而是…」vs W34「把三條線並排，這週的張力不是…也不是…而是…」逐字級同構）
8. 🔧 **數字紀律**——關鍵數字第一次出現時句內附（來源，日期）；**同段 ≥2 個同單位數量時，每個數字緊鄰處必須帶角色詞**（已實現／年化／單季／預測（年份）／估值／額度上限／一次性），同段 ≥3 個角色互異 → 拆句或移「本週數字」；同段具名機構／媒體 ≥3 家 → 概括為「N 家媒體同步」，不逐一列名。（反例：W33 首段六個金額、其中兩個還是同一收購案的互斥數字）
9. 🔧 **日期位置**——每段以 `MM-DD` 開頭的句子 ≤1（留給該段真正以時序為重點的那句），其餘事件先行、日期後置（句中補述或括號）；段內日期由早到晚，做不到代表混了兩條時間線 → 拆段。（反例：W33 首段日期序 08-11→08-10→08-13→08-15，第二句把讀者拉回前一天）
10. 🔧 **粗體預算＋案例定性**——頭條全節粗體 ≤2 處、只標數字／專名、單處 ≤15 字，不標完整判斷句。引用具體使用者案例時**當句交代**它是個案、已知模式、還是本期確認的新機制，不留給回收表。（反例：W34 最有力的一句「排程被切到 Fable 5」，讀者要讀到回收表才知道它是第三種靜默替換機制）

##### 驗收層：冷讀者三問（頭條寫完後強制執行，不進交付檔）

假裝你是第一次讀本刊、只讀了頭條敘事的人，回答固定三問，**每個答案必須是頭條正文中可逐字引用的連續文字**（附引用），不得用腦中背景知識補：

1. 這週最壞的具體情況是什麼、發生在誰身上？
2. 和上一週相比，**變的**是什麼？（答案要是變化，不是狀態）
3. 讀完之後，該對哪一件事保持懷疑？（哪個說法還沒被證實）

任一問找不到可引用的連續文字 → 回頭改頭條（**補一句，不是加一段**），不得以「這在深挖有寫」放行。三問與引用寫入完成回報，供收尾檢視。（實測：W34 三問掛兩問——Q2 頭條無任何與上週的對照、Q3 該懷疑的兩件事（WIRED 繞過宣稱、`/design` 單一來源）頭條零暗示；各補一句即修復）

> 刻意不規定的維持不變：語氣詞彙、句長、比喻用不用。收束預算管的是**密度**不是禁令——金句是預算制，全篇留一個記憶點，它反而更值錢。

#### (2) 技術討論＋深挖

- 開頭固定 **2–3 行「本週版本」**：升版 go/no-go＋breaking change 提醒（無大事一行帶過）
- **討論綜述**：本週社群在吵什麼、測什麼（廣度，**半頁上限**；每條給冷讀者一句話脈絡）
- **深挖專欄**（獨立小標 `### 深挖：主題名稱`，**800–1,200 字**）：教學式深挖——前 1/3 基礎快講（照顧冷讀者），後 2/3 進階深挖（機制、帳目、坑）

  > ⚠️ 小標是 **`###`**——它是輸出檔 `## 二、技術討論與深挖` 的子標題，與同層的「本週版本」「討論綜述」齊平。**不要照抄本規格檔自己的標題深度**：本檔在這裡是 `#### (2)`，輸出檔少一層，字面照抄會矮一級、失去「專欄從這裡開始」的結構訊號（2026-08-16 W33 踩過；規格原本的範例就寫成 `####`，W30–W32 三期各自從輸出結構推導出 `###` 而沒人回頭改規格，於是錯誤範例活了三週）。
  >
  > 字數 800–1,200 是 2026-08-16 依 W30–W33 實測（999／1,112／1,080／1,142）校準的；原訂 400–600 從未有任何一期遵守，也沒有任何機制去比對。兩項現由 `scripts/check_weekly_ledger.py` 機械檢查。

**通則四修（防綁死／防雜燴／防假教學／防重複）：**

| 修 | 規則 |
|---|---|
| a. 防綁死 | 題目**優先**從討論綜述選，但可從當週任何技術材料選（版本、官方公告、獨立文章） |
| b. 防雜燴 | 深挖必須有獨立小標與字數框，結構上看得出「專欄從這裡開始」 |
| c. 防假教學 | 入選判準：這題必須能教出**機制層**的東西（讀者學完能解釋為什麼）；達不到 → 換長燒 issue 機制解剖當備援題；再不行 → 本週省略，不硬寫 |
| d. 防重複 | 對照步驟 3 的已深挖題目清單；重複題必須有新角度才准再上 |

##### 選題三判準 `[加入: 2026-08-16]`

題目**由本週討論熱度決定，不由本週素材密度決定**。三條全過才寫：

1. **本週有訊號**——日報或討論綜述至少一則相關條目，且開頭一句要說得出「為什麼是這週」。沒有本週訊號 → 那是常設教學，屬 `wiki/topics/coding-workflow-guide`，不是週報深挖
2. **寫得出「寫作方向三件套」**（見下）——寫不出來代表這題還沒想清楚，**此刻換題，而不是寫到一半才發現**
3. **每個機制斷言可指回可取回的來源**（見「來源紀律」）

**優先序：本週熱點 × 讀者興趣 `[加入: 2026-08-20]`。** 同時有多題過三判準時，**命中 `wiki/reader-notes.md` ⏳ 🔍 興趣主題者優先**——那代表讀者主動問過、而庫內覆蓋不足，是需求面已被證實的題目，比單純熱度高的題目值得寫。命中時在深挖開頭的「為什麼是這週」一句裡帶出這層（例：「這題你問過，本週剛好有官方文件可以回答」），並在檔尾涵蓋窗註明命中哪一條。

> 這條補的是一個結構缺口：`reader-notes.md` 原本只被 `/wiki-weekly-review`（對內策展）與 `/wiki-ingest`（逾期提醒）消費，**對外交付的週報從不讀它**——於是讀者問過的東西只會變成 wiki 頁面加碼，永遠進不了他們真正在讀的那篇。深挖寫完若解掉了某條 🔍，回報中提醒使用者可將該筆標 ✅（本指令不自行改該檔狀態，避免與 `/wiki-weekly-review` 的消費權責重疊）。

##### 寫作方向三件套（動手前必須先寫出來）

| 項目 | 要求 |
|---|---|
| **一句讀者動作** | 讀完會改變的**具體**事，必須指名對象：旗標／檔案／指令／數值門檻／決策規則。只答得出「他會更了解這件事怎麼運作」→ 那是評論不是深挖，換題 |
| **四段大綱** | 基礎快講要講什麼、機制層要解釋哪一個「為什麼」、會咬人的地方預計幾條、怎麼用收在哪句判斷 |
| **缺口清單** | 四段裡哪幾格現在沒有素材——這是外查的**目標清單**，讓查找有方向而不是漫無目的補料 |

##### 來源紀律 `[加入: 2026-08-16]`

不限來源位置，只有一條：

> **機制層的每個斷言都要能指回一個可取回的來源**（URL ＋ 取得日期），並在正文標明。
> 唯一豁免是**從已標來源的事實推導出的結論**，但推導過程要看得見，且結論標「（推論）」。
> 兩者皆非 → 那是撰稿者的通用工程知識，**刪掉**。

有缺口就去查（WebFetch／WebSearch），不要因為素材不足而降格題目或灌水撐字數。

> ⚠️ **無 egress 環境的退路**：外查依賴網路。本指令目前只在本機執行（`/weekly` 無雲端排程，見步驟 6），故不受影響；**若日後上了雲端排程，該環境 egress 封鎖、外查步驟不可用**，該期必須改寫素材自足的備援題，並在檔尾註明「本期於無外查環境產出」，不得靜默地少查。

##### 寫作風格（依 W30–W32 實測歸納，W33 為反例）`[加入: 2026-08-16]`

**四段骨架，每段帶粗體功能標籤**（讀者要能跳讀）：

```
**基礎快講**          定義 ＋ 與相鄰概念的區分          ~15%
**機制層**            為什麼會這樣（一層新的解釋）      ~20%
**N 個會咬人的地方**  編號陷阱，每條獨立                ~45%  ← 價值密度最高，不可省略
**怎麼用**            一句 if/then 決策規則             ~20%
```

**六條寫作規則：**

1. **每個斷言帶具名可驗證物**——參數名、預設值、錯誤碼、版本號、檔名、指令。W30 有 `low/medium/high/xhigh/max`、預設 `high`、送 `thinking: disabled` 回 400、`max_tokens` 從 64k 起調；W33 只有別人的四個數字，沒有一個是讀者能自己設的東西
2. **用對比定義新概念**，不用定義句（W30：「`thinking` 控制要不要思考，`effort` 控制整個回應花多少 token」）。冷讀者靠差異建座標比靠定義快
3. **第二人稱＋操作現場**（W32：「你在終端機打 `claude` 之後、還沒輸入任何東西之前」）
4. **陷阱編號且各自獨立**，每條＝為什麼咬人 ＋ 正確做法，不合成散文
5. **結尾是決策規則，不是總結**（W30 收在「先在 effort 這條軸找到工作點，再考慮是不是真要換模型」）
6. **邊界說明內嵌在證據旁**，禁止獨佔結尾段——誠實要散在正文裡，不是堆成免責聲明

**三條禁止：**

- ❌ 同一句話換說法重講（W33 把「訂閱制賣產能不賣 token」講了四次——那不是強調，是沒有第二層機制）
- ❌ 沒有具名物的形容詞（「效能不錯」「有落差」）；量不到就不寫
- ❌ 以免責聲明收尾（讀者最後印象會變成全篇不可信）

> 刻意不規定的：語氣詞彙、句長、比喻用不用——不可檢查的規則寫進規格只會變成裝飾。

#### (3) 下週看什麼

本段含**兩張方向相反的表**，必須用下列固定小標與**固定欄名**寫，`scripts/build_web.py` 依欄名分辨兩者（欄名改動會讓該表整張不進 JSON、在網站上消失）：

```markdown
### 先回收上週（Wnn）的帳

判準欄逐字沿用立案當期原文，未結案者續盯至 Wnn+1。

| 上週預告 | 判準 | 本週結果 |
|---|---|---|
| … | 逐字沿用立案當期原文，不得改寫 | ✅／❌／⏰ 結案，或 ⏳／🟡 + 「→ 續盯至 Wnn」 |

### 本週新開 N 條

（一句話說明哪些續盯條已在上表、不重複佔新開額度；無續盯條時寫本期無續盯。）

| 類型 | 預告 | 判準 |
|------|------|------|
```

> **兩張表各自的導言都不可省略。** 回收表那行會被 `scripts/build_web.py` 抽成 `nextweek.intro` 並顯示在網站上；新開表那行**目前不進網站**（`_parse_weekly_nextweek_intro` 只取第一個 `|` 之前的文字，`app.js` 也只渲染 `intro`／`recap`／`forecasts`），但它在 Obsidian 與原始檔裡回答「為什麼追蹤 7 條卻只新開 5 條」，仍是必寫項。兩者皆由 `scripts/check_weekly_ledger.py` 以 ⚠️ 提醒。

`scripts/check_weekly_ledger.py` 依上述欄名與標題比對兩期帳目，掛在 `scripts/run_tests.py` 內。

> 小標與表格之間那一行導言**不可省略**——`scripts/build_web.py` 把它抽成 `nextweek.intro`，缺了網站上該段會從小標直接跳進表格，與前幾期不一致（2026-08-16 W33 踩過；W30–W32 三期都寫了，但本範本原本沒畫這一行）。

**帳目生命週期 `[加入: 2026-08-02]`**：回收表要涵蓋的是**上一期的整本帳**——上期新立的 ＋ 上期回收表中仍未結案（⏳／🟡）的，兩者都必須逐條出現，漏一條即測試失敗。

| 結果 | 下一期 |
|---|---|
| ✅／❌ 判準被切乾淨 | 結案，不再出現 |
| ⏰ 到期日已過 | 結案；結果重要則轉入 wiki 對應頁，於結果欄註明去向 |
| ⏳ 未定／🟡 半收 | **留在帳本這一側續盯**，結果欄寫「→ 續盯至 Wnn」，**不佔新開條數額度** |
| 同一條連續兩期未定 | **強制結案**，寫「無結論」或降級為未證實——避免殭屍條目長住帳本 |
| 判準因事件性質改變而失效 | 結案並註明「判準失效（原因）」，要續追改立新條，不得沿用舊判準 |

**可證偽預告**：每條立判準「若 X 則 A、若 Y 則 B」。

**判準必須含 null 分支 `[加入: 2026-08-02]`**：二分法只涵蓋「發生了 X」與「發生了 Y」，但實務上**最常見的結果是「這週什麼都沒發生」**——W30 六條有三條落在此格，只能寫「未定」，等於該條預告整週未產生資訊。因此除到期日型外，每條判準都要寫明**無事發生時的處置**（順延 N 週／降級為未證實／併回既有敘事／結案），例如「若兩週內只剩體感抱怨 → 併回既有共識，不另立線」。

**判準必須可查證 `[加入: 2026-08-02]`**：判準的作用是讓回收變成**查證**而非**判斷**——寫成主觀敘述（「社群覺得有改善」）時，回收者既立判準又判結果，等於自己給自己打分。每條判準結尾必須附查證線索，格式固定：

```
…判準文字…｜查證：關鍵字1、關鍵字2
```

關鍵字須是**能在 `news/*.md` 直接 grep 到的字串**（產品名、issue 編號、版本號、機構名），不可是形容詞。日更 pipeline 會在**選材完成後**用這些關鍵字掃當日條目，命中則 append 至 `weekly/open-signals.jsonl` 供下期回收取用（見 `.claude/commands/news-pipeline-steps.md` Step 3e）。

續盯條目若沿用的是舊判準（無查證線索），回收時補上——`scan_open_forecasts.py` 會對缺線索者印 ⚠️，那是提醒不是錯誤。

> ⚠️ 掃描一律在選材之後執行。若讓選材階段知道週報正在賭什麼，會產生確認偏誤——選材傾向撿能證實預告的條目，命中率虛高，並連帶破壞每月聚焦校準的獨立性（校準量測的正是選材品質，兩者不得互相知情）。

**條數 3–6，寧缺勿湊 `[加入: 2026-08-02]`**：可證偽是有成本的，湊數會混進「其實沒把握怎麼驗」的題目（W30 六條僅 1 條被判準切乾淨）。每條入選前先過一關：**這個判準能用日報 grep 驗嗎？** 答不出關鍵字 → 不立此條。

第一期（無上一期可回收）時省略回收表，只寫新開表。

條目六類（**技術類——修復追蹤、趨勢確認——優先選**）：

### 6. 收尾閉迴路 `[加入: 2026-07-26]`

> **由 `/weekly` 帶起時跳過本步驟**（`.claude/commands/weekly.md` 會在兩個子指令都跑完後統一收尾）。只有單獨執行 `/weekly-report` 補跑時才執行以下內容。

**沒有這一步，週報只會躺在工作目錄裡**：未 commit（違反根目錄 `CLAUDE.md` 的完工定義）、未 build（web reader 的「週報」分頁仍顯示「尚無週報」）、未 push（線上看不到）。形狀與 `.claude/commands/news-pipeline-steps.md` 的 `Step 4`／`Step 5` 一致：

```
git -C REPO_ROOT add weekly/
git -C REPO_ROOT commit -m "weekly: YYYY-Wnn 週報"

PYTHON REPO_ROOT\scripts\run_tests.py
# 失敗 → 跳過 build，但仍推送已完成的 weekly commit，並在回報標「Tests FAILED - build skipped」

PYTHON REPO_ROOT\scripts\build_web.py
git -C REPO_ROOT add web_reader/
git -C REPO_ROOT commit -m "web: rebuild YYYY-Wnn 週報上站"

git -C REPO_ROOT push        # 單一 push
```

- **單一 push**：每次 push 觸發一個 GitHub Pages 部署，分多次會互相搶佔導致線上停在舊版
- **push 失敗**：照 `.claude/commands/news-pipeline-steps.md` 的 `Step 5` push 失敗重試程序處理（`pull --rebase` 上限 2 次），不要另寫一套
- **與排程的關係**：`/weekly` 沒有雲端排程，不會與 `daily-news-pipeline-cloud`（每日 22:00 UTC（台北隔日 06:00））或 `weekly-wiki-lint-cloud`（每週六 03:00 UTC（台北 11:00））衝突；產出檔在 `weekly/`，與那兩者會動的 `news/`、`wiki/` 不重疊。若執行時間逼近排程時點，靠上述 push 重試化解

## 編輯守則

- **淡週寧短勿編**：本週材料單薄時，各段落寧可寫短，不可為了填滿篇幅硬湊。
- **查無不補位**：任一段落（尤其深挖專欄）找不到夠格的題目時，直接省略該段並註明「本週略過」，不可用不夠格的材料硬填。
- **引用具名出處**：所有事實性陳述附具名來源（媒體名、issue 編號、討論串連結等），不可空泛歸因「社群」「有人」。
- 與 `.claude/commands/wiki-weekly-review.md` 分工寫死：`/wiki-weekly-review` 是對內策展（wiki 頁面加碼判斷），`/weekly-report` 是對外交付（週報產出）——**兩者由 `/weekly` 依序帶起，但不可合併成同一段工作**。三個理由：(a) 確認閘相反——策展未經使用者確認不得改頁，週報是自主產出；(b) 凍結語義衝突——週報寫完即凍結，策展則主動改 wiki，同段執行會讓週報引用到自己剛改出的狀態；(c) 帳本獨立性——策展若知道週報開了哪些預告，會傾向加碼能讓預告成真的主題（同第 (3) 段對選材的確認偏誤警告）。**故執行順序固定為週報先、策展後**，見 `.claude/commands/weekly.md`。
- 互動數（讚數、留言數等）一律標「（MM-DD 快照）」，避免讀者誤判為即時數字。
