# Weekly Report — 週報產生

> **這是週報本體，不是每週的入口。** 平常跑 `/weekly`（總指揮，會依序帶起本指令與 `.claude/commands/wiki-weekly-review.md`）；單獨執行本指令只在補跑或修正單一期週報時使用。
> 單獨執行時，收尾（步驟 6）由本指令自己負責；由 `/weekly` 帶起時，**步驟 6 一律跳過**，收尾交給總指揮統一做（單一 push，理由見該檔）。

「當週技術新聞的教學式深挖」專欄。題目跟新聞走（本週最有料的技術題），寫法是教學的（基礎快講＋進階深挖混合深度），**不是預排課綱**。

**讀者：** 使用者自己＋會分享給別人（冷讀者要能讀懂，基礎概念不可跳過）。
**全文 5 分鐘讀完。**

---

## 使用方式

- `/weekly-report`：產生本週（今日所在 ISO 週）的週報
- `/weekly-report 2026-W30`：指定週次（用於補跑或修正）

平常不直接下這個指令——見檔首說明，每週入口是 `/weekly`。

---

## 步驟

### 1. 決定週次與輸出路徑

取 ISO 週號（若 `$ARGUMENTS` 指定則用指定值，否則用今日所在週），輸出至 `weekly/YYYY-Wnn.md`（`weekly/` 目錄不存在則建立）。

### 2. 蒐集素材

固定涵蓋窗：**近 7 日** `news/*.md`（唯讀，不可修改）＋ `wiki/log.md` 同期 ingest 紀錄＋ `wiki/feature-radar.md`。

### 3. 檢查已深挖題目清單（防重複）

掃描既有 `weekly/*.md`（若有）的「深挖：」小標題，列出近期已深挖過的題目。本週選題撞到舊題目時，必須有**新角度**（新事實或新機制層）才准再上；否則換題。

### 4. 撰寫四段式結構

#### (1) 頭條敘事

當週最大張力縫成一條因果敘事，**300–500 字，不列清單**。

#### (2) 技術討論＋深挖

- 開頭固定 **2–3 行「本週版本」**：升版 go/no-go＋breaking change 提醒（無大事一行帶過）
- **討論綜述**：本週社群在吵什麼、測什麼（廣度，**半頁上限**；每條給冷讀者一句話脈絡）
- **深挖專欄**（獨立小標 `### 深挖：主題名稱`，**800–1,200 字**）：教學式深挖——前 1/3 基礎快講（照顧冷讀者），後 2/3 進階深挖（機制、帳目、坑）

  > ⚠️ 小標是 **`###`**——它是輸出檔 `## 二、技術討論與深挖` 的子標題，與同層的「本週版本」「討論綜述」齊平。**不要照抄本規格檔自己的標題深度**：本檔在這裡是 `#### (2)`，輸出檔少一層，字面照抄會矮一級、失去「專欄從這裡開始」的結構訊號（2026-08-16 W33 踩過；規格原本的範例就寫成 `####`，W30–W32 三期各自從輸出結構推導出 `###` 而沒人回頭改規格，於是錯誤範例活了三週）。
  >
  > 字數 800–1,200 是 2026-08-16 依 W30–W33 實測（999／1,112／1,080／1,142）校準的；原訂 400–600 從未有任何一期遵守，也沒有任何機制去比對。兩項現由 `scripts/check_weekly_ledger.py` 機械檢查。

**通則四修（防綁死／防雜燴／防假教學／防重複）：**

| 修 | 規則 |
|---|---|
| a. 防綁死 | 題目**優先**從討論綜述選，但可從當週任何技術材料選（版本、官方公告、獨立文章） |
| b. 防雜燴 | 深挖必須有獨立小標與字數框，結構上看得出「專欄從這裡開始」 |
| c. 防假教學 | 入選判準：這題必須能教出**機制層**的東西（讀者學完能解釋為什麼）；達不到 → 換長燒 issue 機制解剖當備援題；再不行 → 本週省略，不硬寫 |
| d. 防重複 | 對照步驟 3 的已深挖題目清單；重複題必須有新角度才准再上 |

#### (3) 下週看什麼

本段含**兩張方向相反的表**，必須用下列固定小標與**固定欄名**寫，`scripts/build_web.py` 依欄名分辨兩者（欄名改動會讓該表整張不進 JSON、在網站上消失）：

```markdown
### 先回收上週（Wnn）的帳

| 上週預告 | 判準 | 本週結果 |
|---|---|---|
| … | 逐字沿用立案當期原文，不得改寫 | ✅／❌／⏰ 結案，或 ⏳／🟡 + 「→ 續盯至 Wnn」 |

### 本週新開 N 條

| 類型 | 預告 | 判準 |
|------|------|------|
```

`scripts/check_weekly_ledger.py` 依上述欄名與標題比對兩期帳目，掛在 `scripts/run_tests.py` 內。

**帳目生命週期 `[加入: 2026-08-02]`**：回收表要涵蓋的是**上一期的整本帳**——上期新立的 ＋ 上期回收表中仍未結案（⏳／🟡）的，兩者都必須逐條出現，漏一條即測試失敗。

| 結果 | 下一期 |
|---|---|
| ✅／❌ 判準被切乾淨 | 結案，不再出現 |
| ⏰ 到期日已過 | 結案；結果重要則轉入 wiki 對應頁，於結果欄註明去向 |
| ⏳ 未定／🟡 半收 | **留在帳本這一側續盯**，結果欄寫「→ 續盯至 Wnn」，**不佔新開條數額度** |
| 同一條連續兩期未定 | **強制結案**，寫「無結論」或降級為未證實——避免殭屍條目長住帳本 |
| 判準因事件性質改變而失效 | 結案並註明「判準失效（原因）」，要續追改立新條，不得沿用舊判準 |

**可證偽預告**：每條立判準「若 X 則 A、若 Y 則 B」。

**判準必須含 null 分支 `[加入: 2026-08-02]`**：二分法只涵蓋「發生了 X」與「發生了 Y」，但實務上**最常見的結果是「這週什麼都沒發生」**——W30 六條有三條落在此格，只能寫「未定」，等於該條預告整週未產生資訊。因此除到期日型外，每條判準都要寫明**無事發生時的處置**（順延 N 週／降級為未證實／併回既有敘事／結案），例如「若兩週內只剩體感抱怨 → 併回既有共識，不另立線」。

**判準必須可查證 `[加入: 2026-08-02]`**：判準的作用是讓回收變成**查證**而非**判斷**——寫成主觀敘述（「社群覺得有改善」）時，回收者既立判準又判結果，等於自己給自己打分。每條判準結尾必須附查證線索，格式固定：

```
…判準文字…｜查證：關鍵字1、關鍵字2
```

關鍵字須是**能在 `news/*.md` 直接 grep 到的字串**（產品名、issue 編號、版本號、機構名），不可是形容詞。日更 pipeline 會在**選材完成後**用這些關鍵字掃當日條目，命中則 append 至 `weekly/open-signals.jsonl` 供下期回收取用（見 `.claude/commands/news-pipeline-steps.md` Step 3e）。

續盯條目若沿用的是舊判準（無查證線索），回收時補上——`scan_open_forecasts.py` 會對缺線索者印 ⚠️，那是提醒不是錯誤。

> ⚠️ 掃描一律在選材之後執行。若讓選材階段知道週報正在賭什麼，會產生確認偏誤——選材傾向撿能證實預告的條目，命中率虛高，並連帶破壞每月聚焦校準的獨立性（校準量測的正是選材品質，兩者不得互相知情）。

**條數 3–6，寧缺勿湊 `[加入: 2026-08-02]`**：可證偽是有成本的，湊數會混進「其實沒把握怎麼驗」的題目（W30 六條僅 1 條被判準切乾淨）。每條入選前先過一關：**這個判準能用日報 grep 驗嗎？** 答不出關鍵字 → 不立此條。

第一期（無上一期可回收）時省略回收表，只寫新開表。

條目六類（**技術類——修復追蹤、趨勢確認——優先選**）：

- 到期日型
- 矛盾待解型
- 修復追蹤型（技術類，優先）
- 官宣待發型
- 傳聞驗證型
- 趨勢確認型（技術類，優先）

#### (4) 檔尾數字

**5 個數字收尾**：

- 故事型（編輯挑，1–2 個能代表本週故事的數字）
- 管線型（收錄漏斗、Status 事故數、版本數、最高互動 issue 留言數、wiki 更新頁數等）

第一版**人工數**（從步驟 2 的素材手動盤點）；第二期規劃轉 `scripts/weekly_stats.py`（尚未建置，見下方「後續」）。

### 5. 凍結存檔

寫入 `weekly/YYYY-Wnn.md` 後視為當週凍結版本，不因後續 ingest 回頭修改（下週報若要回收上週對錯，於新一期第 (3) 段處理，不修舊檔）。

### 6. 收尾閉迴路 `[加入: 2026-07-26]`

> **由 `/weekly` 帶起時跳過本步驟**（`.claude/commands/weekly.md` 會在兩個子指令都跑完後統一收尾）。只有單獨執行 `/weekly-report` 補跑時才執行以下內容。

**沒有這一步，週報只會躺在工作目錄裡**：未 commit（違反根目錄 `CLAUDE.md` 的完工定義）、未 build（web reader 的「週報」分頁仍顯示「尚無週報」）、未 push（線上看不到）。形狀與 `.claude/commands/news-pipeline-steps.md` 的 `Step 4`／`Step 5` 一致：

```
git -C REPO_ROOT add weekly/
git -C REPO_ROOT commit -m "weekly: YYYY-Wnn 週報"

PYTHON REPO_ROOT\scripts\run_tests.py
# 失敗 → 跳過 build，但仍推送已完成的 weekly commit，並在回報標「Tests FAILED - build skipped」

PYTHON REPO_ROOT\scripts\build_web.py
git -C REPO_ROOT add web_reader/
git -C REPO_ROOT commit -m "web: rebuild YYYY-Wnn 週報上站"

git -C REPO_ROOT push        # 單一 push
```

- **單一 push**：每次 push 觸發一個 GitHub Pages 部署，分多次會互相搶佔導致線上停在舊版
- **push 失敗**：照 `.claude/commands/news-pipeline-steps.md` 的 `Step 5` push 失敗重試程序處理（`pull --rebase` 上限 2 次），不要另寫一套
- **與排程的關係**：`/weekly` 沒有雲端排程，不會與 `daily-news-pipeline-cloud`（每日 13:00 UTC）或 `weekly-wiki-lint-cloud`（每週六 01:00 UTC）衝突；產出檔在 `weekly/`，與那兩者會動的 `news/`、`wiki/` 不重疊。若執行時間逼近排程時點，靠上述 push 重試化解

## 編輯守則

- **淡週寧短勿編**：本週材料單薄時，各段落寧可寫短，不可為了填滿篇幅硬湊。
- **查無不補位**：任一段落（尤其深挖專欄）找不到夠格的題目時，直接省略該段並註明「本週略過」，不可用不夠格的材料硬填。
- **引用具名出處**：所有事實性陳述附具名來源（媒體名、issue 編號、討論串連結等），不可空泛歸因「社群」「有人」。
- 與 `.claude/commands/wiki-weekly-review.md` 分工寫死：`/wiki-weekly-review` 是對內策展（wiki 頁面加碼判斷），`/weekly-report` 是對外交付（週報產出）——**兩者由 `/weekly` 依序帶起，但不可合併成同一段工作**。三個理由：(a) 確認閘相反——策展未經使用者確認不得改頁，週報是自主產出；(b) 凍結語義衝突——週報寫完即凍結，策展則主動改 wiki，同段執行會讓週報引用到自己剛改出的狀態；(c) 帳本獨立性——策展若知道週報開了哪些預告，會傾向加碼能讓預告成真的主題（同第 (3) 段對選材的確認偏誤警告）。**故執行順序固定為週報先、策展後**，見 `.claude/commands/weekly.md`。
- 互動數（讚數、留言數等）一律標「（MM-DD 快照）」，避免讀者誤判為即時數字。
