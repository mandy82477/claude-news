# 開發實務（devpractice）記者：負責頁的維護契約

每日與每週各做什麼在 `.claude/reporter-rules/devpractice/daily.md`、`.claude/reporter-rules/devpractice/weekly.md`；本檔只寫頁面本身的契約。

## topics/coding-workflow-guide

### 程式開發實戰手冊維護

本頁回答「用 Claude Code 寫程式時，每個流程階段官方怎麼做、社群補了什麼、哪裡還沒有答案」——照階段查，不照工具查；不承諾「該下哪個 skill」。整頁由你一人維護。領域欄是 💻 開發實務，`scripts/pending_handoffs.py` 的領域對照沒有這一類，負責人靠同檔 `OWNER_OVERRIDES` 指到你。

三條進料：

| 進料 | 節奏 | 觸發邊 |
|---|---|---|
| **官方對既有功能的使用指南**（省 token、session 經營、設定建議，無新指令旗標） | 每日 | 分類層把這類條目標成「開發實務」，派工包隨每日沉澱一起給你（`.claude/skills/wiki-ingest/references/classification.md`「分流鐵則：官方內容不是社群類的禁區」） |
| 候選帳本 | 每週 | `python scripts/devpractice_diff.py pending` 列出還沒處理的候選 |
| 技能清冊與社群工具策展 | 每週 | 本節下方「週更動作」——類別路由接不到，本節即其觸發邊 |

**官方使用指南的寫入紀律：** 寫進對應的流程階段節，與該節既有的「官方的…」子節並列；**必附官方原文連結與發布日期**。它是本頁唯一可以來自新聞條目的內容，放行理由是它有一手來源、會被更新、經得起查證。社群做法走週更，不因本條放行而每日寫入。

**軸線鐵則：** 以**工程流程階段**為軸（本頁第 1–9 段：寫專案指示檔→探索→規劃→動手寫→review→測試與上線→規則跟上改動→規則保鮮→除錯），**不得改以開發領域（嵌入式／遊戲／資料工程）分欄或分列**。官方做法本身不按領域切，照領域組織會產出大量空格；領域差異只在有具體依據時，於該段寫一句，沒有依據就不寫。

**每段是現在的答案，不是更新紀錄：** 寫入時改寫該段既有的句子或表列，不在段尾追加「某月某日新增」。段內同一件事只留最新說法，舊說法刪掉。

**自足，但事實只有一個家：** 讀者只讀這頁就要拿得到每一段可照做的答案。別頁才有的細節（計費估法、issue 狀態、版本表、模型預設值），本頁留一句讀者語言＋關鍵數字（價錢、上限、方案、版本），再用 `[[頁#標題]]` 錨點指到那一頁；不整段重抄，也不只丟一個連結讓讀者自己去找答案。額度、定價、單一模型的新聞不進本頁正文，家在 `entities/pricing`、各模型頁與 `topics/model-comparison`。

**標題與正文不寫進度：** 段標題不帶 `[已深查]` 這類狀態標記——頁內所有 `](#…)` 連結（目前在「我想問的是」「這條流程長什麼樣」「本週 coding 亮點」與第 9 段）的錨點都由標題算出，標題一改錨點就斷；改標題時用 `grep -n '](#' wiki/topics/coding-workflow-guide.md` 全數同批改。正文不寫「社群面（某日補）」「本庫某日移除追蹤」這類維護經過，要留就進 `%% %%`。段號 1–9 被 `data/skill_interest_watch.json` 的 `guide_section` 與 `wiki/index.md` 引用，改段號要開轉知請兩處同批改。

**週更動作：**

1. **候選落地**：`python scripts/devpractice_diff.py pending` 列出的每一筆，問「它改變了哪個流程階段的做法」。答得出 → 先開候選的原頁確認現況（issue 可能已修、說法可能已被更正，帳本那一句是撿到當天的狀態），再改那一段，事實細節以 wikilink 指回原頁；答不出、或原頁已不支持 → 不寫。全部看完才跑 `python scripts/devpractice_diff.py consume`。
2. **技能清冊**：讀 `Official Skills` 來源近 7 天條目（`src/news_aggregator/sources/official_skills_repos.py` 偵測到的清冊異動）。會改變某個流程階段做法的新 skill，寫進該段；屬產出物格式的，改「附錄：產出物格式類 skill」；屬非工程用途不進本頁。清冊有增減時，同步自查寫「⚠️ 需主編轉知功能記者：`entities/claude-skills` 生態動態」。
3. **流程表「缺什麼」欄**：某段的缺口被新的官方機制補上時，改「這條流程長什麼樣」表那一列的官方欄、燈號與缺什麼欄，同步自查寫「⚠️ 需主編轉知功能記者：`official-community-gap` 矩陣」。
4. **探錯模式回訪**：比對近 7 天 patterns 樹（`community-tech-patterns` 母頁與七個子頁）新節點，判斷有無解掉、取代或補強第 2b 段「探錯時會看到什麼」的某一種。有則更新該條，無則不動。
5. **缺口回訪**：段內寫著「還沒解掉」「缺什麼」的缺口，本週候選或 patterns 樹有對應證據才補，補了標來源與日期，並回頭改流程表該列的燈號（第 3 步）；沒有就不動，不拿通用工程常識填。
6. **本週 coding 亮點**（節位置在「目前結論」之後）：覆寫，至多三條，只放本週真的改了正文的地方，每條一句加指向該段的錨點；檢查日與「其餘候選屬他頁」這類說明寫進該節的 `%% %%`。本週正文沒動就留一行 `> 本週無新亮點（YYYY-MM-DD 檢查）`。
7. 清冊查證日更新於「參考來源」。清冊性更新不動「最後新聞更新」；當日有官方使用指南寫入時才動。

`## 6. 測試與上線` 段末保留一行指向 [[topics/anthropic-agent-stack]]「你該用哪個」的出口，連頁不連錨。

**不做的事：** 不從通用工程知識補內容；不記錄各 skill 的內部實作細節；不重述事實頁已寫的版本與 issue 細節。
