### 深挖：本期兩篇記者專文

第一篇講一個官方文件沒寫的機制，第二篇講一個沒有人拿出證據的爭議。兩篇各約三分鐘。

#### 功能｜Claude Code 長對話會靜默清掉工具輸出，你該先存成檔案

**基礎快講** 工具輸出指 Bash 結果、讀檔內容、grep 清單這類塞進對話的文字。`/compact` 與 autocompact 是把整段對話壓成摘要，你看得到。本文講的是另一種：只把舊的工具輸出換掉，其餘對話不動。官方 [context window 文件](https://code.claude.com/docs/en/context-window)（10-03 取得）全文找不到 microcompact 一詞，也沒有說明工具輸出清除。[issue #42542](https://github.com/anthropics/claude-code/issues/42542)（04-02 開，10-03 仍 open，29 則留言、11 個讚）至今無維護者回覆。

**機制層** 據該 issue 回報者稱（10-03 取得），有三條路徑：
- 時間型 microcompact：距上一則 assistant 訊息超過遠端門檻，舊結果被換成 `[Old tool result content cleared]`。
- cached microcompact：依計數門檻，用 `cache_edits` 直接從伺服器快取刪除。
- session memory compact：在 autocompact 之前跑，只保留約 40k token 的近期訊息。

回報者並稱 1M 視窗在計數約 80k 時，早期結果已消失。三者門檻由 GrowthBook 遠端旗標決定，所以同一版本、不同人的行為可能不同，這點 issue 也有提到。同類機制在 API 端是明文功能：[context editing](https://docs.claude.com/en/docs/build-with-claude/context-editing)（10-03 取得）的 `clear_tool_uses_20250919`，由開發者自己設 trigger 與 keep。（推論）這更像設計行為而非單純 bug，但「清除時不通知」官方沒有任何說明。

**四個陷阱**
1. 關 autocompact 不等於關清除。回報者稱 `DISABLE_AUTO_COMPACT=true` 無效，microcompact 照跑；`DISABLE_COMPACT=true` 則連手動 `/compact` 一起關掉。
2. hook 接不住。[hooks 文件](https://code.claude.com/docs/en/hooks)（10-03 取得）中，PostCompact 只能觀察、exit code 被忽略，且沒有任何針對工具輸出清除的事件。SessionStart 的 `source` 為 `compact` 時，可用 `additionalContext` 把文字加回 context，但只在 compaction 後觸發，接不住上述三種。
3. 存成檔案也有上限。據 [context window 文件](https://code.claude.com/docs/en/context-window)（10-03 取得），compaction 後只會重讀最多五個最近讀過或改過的檔，超過 5,000 token 的只回來路徑（顯示 `Referenced file`）。
4. 升版救不了你。[CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md) 最新 2.1.288（10-03 取得）沒有任何條目提到 microcompact 或 #42542。2.1.286 的模型 fallback 通知只說明 context 是否由 1M 掉到 200K，是另一件事。

**怎麼用** 在會被反覆引用的結果產出當下，寫進檔案，例如 `notes/test-run.md`，單檔壓在 5,000 token 內，並在提示裡點名檔名要求重讀。可再加 matcher 為 `compact` 的 SessionStart hook，用 `additionalContext` 提醒「重讀 notes/」。（推論）它只救 autocompact；靜默清除沒有觸發點，只能靠你自己的提示。若這個 session 要跨三輪以上引用早先的工具輸出，就先落地成檔；若只是查完即用的一次性輸出，不必做。

#### 社群｜Opus 5.5 被降智了？先量自己的 session log

**這週吵什麼**　Opus 5.5 的「降智」貼文本週又多兩篇，都在 r/ClaudeAI，都是單篇貼文。其一是 LiveNerf（09-27 23:20 UTC），自稱即時追蹤模型表現有沒有隨時間變化。其二是 10-01 的「how to measure, how to spot, how to sue」，作者說 Opus 5.5 上線前五、六天表現極佳，近日在原本能處理的複雜任務上失手。這類「懷疑被降 effort」的主張，本刊已收到六則，屬已知模式。反方向的也有。09-29 有人用同一組 skills 各跑三次，分不出 Sonnet 5.5 與 Opus 5.5；09-24、09-25 各有一篇說模型「回來了」，同樣是單篇。上述貼文都沒有可引用的留言數，快照日 10-03。

**證據有多硬**　LiveNerf 的方法、作者、資料與對照組，本刊未能取回原文，所以不知道。「how to sue」指什麼，也未能確認。本週沒有任何一篇附上版本前後的對照。官方方面，10-03 查不到任何針對「Opus 5.5 是否降規格」的說法。

**降智可以是三種不同的事**　模型真的變差，是第一種。token 計量或計費變了，是第二種。你這端的配置造成浪費，是第三種，例如 MCP、subagent、context 管理。貼文只寫得出「感覺」，分不出是哪一種。目前也沒有人回報「改完設定就恢復」，所以三種都排除不掉（推論）。

**官方認過的那一次**　官方在 [04-23 的說明](https://www.anthropic.com/engineering/april-23-postmortem)（2026-10-03 取得）列了三個各自獨立的變更。
- 03-04 起，Claude Code 預設 reasoning effort 由 high 改為 medium，04-07 回復。
- 03-26 上線的「閒置超過一小時就清舊 thinking」優化有 bug，變成每一輪都清，04-10 修復。
- 04-16 加了一句減少冗長的系統提示，內部評測對 Opus 4.6 與 4.7 都掉 3%，04-20 回復。

官方把發現歸功於用 `/feedback` 回報的使用者。這跟本週對得上的是第一項。上期週報寫過，Opus 5.5 的預設 effort 本來就是 medium，比多數模型低一級。所以「變淺了」有一個不必靠降智就成立的解釋（推論），先確認自己的 effort 設定，再談模型。

**怎麼自己量**　挑同一個 repo、同一類任務，取「覺得正常的那幾週」與「現在」兩段。不要跨 repo 比，context 規模差太多。社群工具 [CC-Canary](https://github.com/delta-hq/cc-canary)（2026-10-03 取得）直接讀 `~/.claude/projects/` 下的 JSONL，不需網路、帳號或遙測。它量讀改比、每個使用者輪次的 API 輪次數與 token 數、提前停止等指標，並自動找出分界日。安裝用 `npx skills add delta-hq/cc-canary`，在 Claude Code 裡跑 `/cc-canary 30`。它給 HOLDING、SUSPECTED REGRESSION、CONFIRMED REGRESSION、INCONCLUSIVE 四種判定，但文件沒公布門檻，只能當自己跟自己比的一條線，不是外部基準。它比的是你的歷史，不是版本對版本。另外模型選不定也是前提：`--model` 只吃 family 名，鎖版的要求 [#27892](https://github.com/anthropics/claude-code/issues/27892) 已以 not planned 關閉。

沒有自己兩段對照，就不因這類貼文改設定、換模型或停訂閱；有了對照，才用 effort 設定與 CC-Canary 的判定決定下一步。

### 本週要動的事

- **在 bypassPermissions 或 shell 允許規則下跑 Claude Code 的人**：升到 v2.1.288，修掉 `bash -c` 裡的危險 `rm` 不問就跑（見本週版本）

- **用 Pro／Max 訂閱的人**：打一次 `echo $ANTHROPIC_API_KEY`，有值就從 shell 設定檔拿掉（見討論綜述）
- **自己寫 MCP server 的人**：把 MCP Python SDK 升到最新版（見討論綜述）
- **靠 `sonnet` 別名跑自動化的人**：先跑一輪回歸測試再信任 Sonnet 5.5（見討論綜述）
- **打算因降智貼文換模型或停訂閱的人**：先挑同一 repo、同類任務的兩段 session 比較，再決定（見社群專文「怎麼自己量」）
