## 0. 一句推薦案
> **兩頁都留、都不拆，把「計費編年史」改成「三個結論表打頭、事件流退成證據層」**——pricing 前三分之一新增／重排成三張表（我的方案／一小時多少／事故還在不在），照 `## 通路與乘數` 的**結論表＋細節區＋一行診斷法**形狀；六個累積節補狀態欄、上限與退場句並寫進規則檔；ECM 把三項缺口結案、指標表重算、砍掉與時序重複的「目前結論」。

**被考慮過但不推薦的方向（各一行）：**
- 事故與爭議拆頁不選，因為子故事三題第 ② 題（自己的結論與時序）現在就不成立——它沒有結論層，補完狀態欄才有得判（健檢卡第 7 節已判，使用者已裁決不拆）。
- 成本案例拆頁不選，因為這個子故事**已經有頁**（ECM `## 企業案例`），再拆等於第三份副本。
- 方案表加「配額絕對量」欄不選，因為官方不公布絕對量（verified V2），整欄會是 `—`，撞上 `wiki-ingest-models.md` H 條低資訊欄禁令。
- 一次蒸餾掉全部舊月份不選，因為 `wiki-ingest-format.md` 明訂**每頁至多 2 個時段**，18 個候選時段要 9 週；本波只做 2 個，可讀性靠結論層而非減行數。

**可行性前提（一行）：不需要任何新進料，也拿不到新進料。** 三張表的每個數字都取自庫內既有文字或官方定價頁（已於 `pricing-2026-09-06-verified.md` 查證）；`src/news_aggregator/sources/topic_watch.json` 的 `_global_max` 是 **8**，現有三個 topic（3＋3＋2）已用滿，且 `_rejected` 有 `enterprise-tool-tracker` 因「公開報導層拿不到具名企業內部決策」被否決的先例——成本線申請定向抓取拿不到額度，也大概率同樣命中該先例。pricing 與 ECM 的維護節奏都是每日更新（`wiki-ingest-commercial.md` 負責頁面表），本案不改節奏。

### 2.2 新節 `## 一小時／一個月大概多少`（Q2）
判準句：**一模型一列；口徑固定為官方 Managed Agents 算例的 token 量；官方算過的標「官方算例逐字」，其餘標「推算」，兩者不得混寫成同一種確定性。** 牌價變動時整表重算，不新增第二種口徑。

```
> 口徑固定：**一小時 agent 工作 ＝ 50k 輸入 ＋ 15k 輸出 token ＋ 一個 session-hour**，取自官方 Managed Agents 算例。只有 Opus 5 那列是官方算的，其餘是同一份工作量代入各自牌價的推算，**不是實測**。資料截至 2026-09-06。

| 模型 | 一小時 | 一個月（每天 4 小時 × 22 天） | 這個數字哪來的 |
|------|--------|------|------|
| Opus 5 | $0.705 | 約 $62 | 官方算例逐字 |
| Fable 5.1 | 約 $1.33 | 約 $117 | 推算（$10/$50 牌價代入同一 token 量）|
| Sonnet 5 | 約 $0.33 | 約 $29 | 推算（$2/$10 牌價代入同一 token 量）|

**打平點：Max 5x 月費 $100 ＝ Fable 5.1 約 75 小時、Opus 5 約 142 小時。** 用得比這個少，訂閱比較貴；用得比這個多，訂閱在替你補貼。

**這個表沒告訴你什麼**

- **你的實際 token 量不會是 50k／15k**。要估自己的，先用 `count_tokens` 量一次真實的 prompt，再照上表比例縮放。
- **一整個月的真實落差有人量過，數字比這裡大得多**：訂閱與純 API 之間最高 40 倍，具名企業案例與方法論見 [[topics/enterprise-cost-management]]，本頁不重複列。

- **換一個模型跑同一件工作差多少**（含 tokenizer 換代讓同一段文字多產生約 30% token）不在本頁，見 [[topics/model-comparison#同一份工作，換設定差多少]]。本頁給的是「一小時多少」，那頁給的是「這一件工作多少」。
```

`$1.33` 算式：50k×$10/Mtok ＋ 15k×$50/Mtok ＋ $0.08 ＝ $0.50＋$0.75＋$0.08。L100 指路句同步改為「模型能力與**同一份工作的實付換算**見 [[topics/model-comparison]]；此表只列牌價。」（治冷讀者「指路指錯維度」）。
### 2.3 新節 `## 事故現在還在發生嗎`（Q3）
判準句：**一事故一列，只收狀態為 🔴 或 ⚖️ 者；轉為 ✅／⏸ 即移出表，條目留在事件流。上限 6 列，滿了先移出最後動態最舊的 ⚖️。** 狀態四值定義（寫在表下，供讀者對號）：🔴 未解＝官方未公開回應、也未載明修復版本；✅ 已修＝官方確認或載明修復版本；⚖️ 司法中＝已進入訴訟程序；⏸ 無後續＝距最後動態逾 90 天且無新回報。**這四值不看留言數，只看官方有沒有給出答案**——示範列中 #79337 最後動態 2026-08-07（距今 30 天）仍是 🔴，因為它未逾 90 天且官方無回應。

### 3.2 缺口表三列結案（V6）
四列改為：部門／團隊層預算 **✅**（組織層 spend cap ＋部門層用量報表）、每人 token 報表 **✅**、即時警報 **✅**（備注寫明「是警示不是自動暫停，超額仍會繼續計費」）、混合計費管理 **❌**。判準句：一缺口一列，狀態四選一（✅／🧪 部分回應／❌／⏸ 需求已消失）；標 🧪 逾 90 天無新細節者，備注須寫「官方已 N 天無進一步說明」。
### 3.3 兩表擇一為家、兩節擇一
**費用管控技巧（pricing）與因應策略（ECM）→ 家在 ECM**：ECM 那張表本來就有「適用規模」欄、是策略表；pricing 那 7 列無日期、無來源分級。pricing 整節砍，逐條去向見 map B1–B7。
