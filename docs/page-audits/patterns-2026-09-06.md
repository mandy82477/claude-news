## 1. 使命句候選（≤2）

- **A（推薦）**「社群拿 Claude Code 玩出哪些做法、哪些已經站住腳、哪些還在試」——三段各對得上現有的料：25 列模式概覽的成熟度三值（L52–81）、115 則帶來源與成熟度的第一手節點（L163–1083）、缺口追蹤的「官方補了沒」（L139–161）。它不承諾「現在主流是什麼」，因為本頁沒有任何欄位在量那件事（見第 4、10 節）。
- **B**「一個模式從社群冒出來、被驗證、到被官方吃掉，中間發生了什麼」——演進版，把缺口追蹤與成熟度當主軸；更有故事但更硬，而 25 列裡有 15 列（60%）是 ⏳ 新興、從未被回訪，撐不起「被驗證」那一段。

**使命句不能寫成「你現在該用哪個模式」**：那是 [[topics/community-tech-tools]]「我卡在這裡」決策表的工作，規則檔已明文分流（`wiki-ingest-community-lint.md`「決策表出口三分流」）。本頁 25 列概覽沒有首選、沒有分界句、沒有最後動態日期，逼它裁決會製造假推薦。

## 8. 證據等級混排

`## 模式概覽`（L52–81）同一張表、同一權重並列：官方基準（L60 Fable 5 orchestrator 46% 成本／96% 效能）、學術論文（L64 arXiv 2607.21656 交叉審查）、單一 dev.to 貼文（L70 Brainless「本日 HN 最高分 124」）、未經佐證的星數（L67 存量盤點條目）。**無硬度欄**，讀者無從分辨哪一列有官方數字撐、哪一列只有一個人寫了篇文章。

## 13. 拆頁三題判

**候選：把 `## 學術對照`＋`### 誰負責拆分`＋`### 缺口追蹤`（L98–161，64 行）獨立成頁。** 三題答：(a) 有自己的問題——「Claude Code 的 agent 機制對得上學術哪些名詞、缺什麼」，reader-notes L18 證明使用者單獨問過；(b) 有自己的結論與時序——有結論（缺口七列＋一項倒退），但**沒有自己的時序**，它是靜態對照不是事件流；(c) 被獨立引用——目前零錨點指入該節。**三題過一半 → 不拆**，它是母故事的一章。該做的是給它「資料截至」與入口句，不是搬家。

**Q5 的落點建議（不裁決，交使用者）：** 「官方 agent 功能→社群玩出哪些配置」的家該在 **official-community-gap**——那頁 L46「Agent 工作模式產品化追蹤」矩陣已經是官方 × 社群的交叉表，反轉讀法或加一欄即可，而本頁是社群視角的證據底，反向索引住這裡會讓功能記者去寫社群記者的頁。但這條要動 `.claude/rules/wiki-ingest-features.md` 的 feature-radar 條目格式（reader-notes L45 自述「屬規則檔層級變更」），**屬新增機制，不是本波單頁改動**。

## 15. 設計起點

**Q2 及格，Q1／Q3／Q4 半拿到、Q5 沒拿到。** 第 2 問（版面達得到嗎）**不及格**，進設計分支。

給設計者一句：**這頁的證據底（115 則帶來源的節點）是全庫最厚的一份，問題全在它上面那 30 行結論層**——25 列概覽表量的是「這個模式多成熟」，而讀者問的是「現在誰在動、我該從哪個開始看」，兩者不是同一把尺；`## 目前結論` 六條裡三條的數字過期，其中一條的錨點還在一個凍結 107 天的頁上。**先給概覽表一個「最後動態」欄與一條退場線（那也會順手清掉四次無人裁決的合併積壓），再把 `## 目前結論` 改成指得回下面 115 則的結論層**，技術彙整不要動。
