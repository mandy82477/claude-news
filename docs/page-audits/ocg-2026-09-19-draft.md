## A-5 新節「官方為什麼還沒補」（取代 L167–179「目前結論」整節；位置移到表格之後）

```markdown
## 官方為什麼還沒補

上面四個 ❌ 裡有兩個、加上「花費估不準」這一面，原因不是「還沒排到」，而是官方的動機本身指向別的方向。這幾段是本頁在別處找不到的東西——但它們說的是**到目前為止**的理由，不是預言：AGENTS.md 曾經也在這一節裡，2026-09-18 官方補了。

**花費為什麼一直估不準**：六個以上的成本監測工具（Tokenyst、CostHawk、Usage4Claude、Throttle Meter、Agent FM 等）反映的焦慮是真的。方案額度與用量拆解官方現在看得到，但「這一次請求為什麼這麼貴」「讓 agent 自己跑三小時會花多少」沒有。官方的產品方向（讓 agent 自主執行更久）在結構上讓花費更難預估，6/15 信用池改制又加了一層。這不是技術做不到，是商業模式：用量變多對 Anthropic 有利。

**CLAUDE.md 寫了它不聽**：Writ（語意規則注入）、Caliber（跨工具設定統一）、Patina（腐化偵測）問的是同一件事——怎麼讓 AI 的行為邊界持久、可維護。官方對複雜 CLAUDE.md 幾乎沒有文件指引，`/doctor`（v2.1.206，2026-07-10）只會建議你把已提交的 CLAUDE.md 寫短，沒有碰到「規則被當成參考脈絡而遭略過」這個核心。

**用 AI 寫久了的副作用**：recap（技能退化）、modularity plugin（技術債加速）、AI 命名一致性（命名漂移）指的是長期隱憂。官方公開敘事（Cat Wu 的「AI 主動性」、Boris Cherny 的「數千子代理深度工作」）方向相反，承認這件事會削弱它自己的說法。

另外兩個 ❌（跨家 agent 的統一操作層、agent 之間的商業往來）不在這一節——它們太新，官方連表態都還沒有，沒有可寫的理由。

**你的選項**：這三件目前都得自己來——花費自己量（企業端的做法見 [[topics/enterprise-cost-management]]）、規則寫短並搭社群的注入工具、副作用靠自己定期回頭讀 agent 寫出來的東西。
```

### 「官方補了沒」表的契約

一張表答一個問題：社群喊的痛，官方補了哪幾個、哪幾個還沒補。**覆寫式**，五欄固定：你痛的是什麼｜官方補了沒｜官方給的是什麼｜還缺什麼、你現在能怎麼辦｜核對日。

**狀態三值，不引進第四值：** `✅` 官方有正式功能可直接用／`🧪` 官方有東西但受限（測試中、須申請、只給企業端）／`❌` 官方目前無對應。判定一律以官方一手為準（官方文件、CHANGELOG、issue 的官方回覆）；頁面自己的舊記錄不得用來反駁一手。

**入口判準（三條全過才開新列）：** ① 這個痛有 ≥2 個獨立社群工具，或一則 GitHub issue ≥100 個讚；② 痛的對象是 Claude Code 或 Anthropic 產品的行為；③ 寫得出「官方補到哪」——查得到官方對應，或已確認官方確實沒有。**上限 18 列**，依狀態排序（`❌` 在最上、`✅` 在最下）。

**退場，只有一條：** `❌` 與 `🧪` 列不退場——缺口還在就留著。`✅` 列在官方功能仍可用期間一律保留；連續 90 天無新社群工具、無新 issue、官方無變動者移出，移出時於該頁 `## 時序` 記一行。**還在跑的產品行為不因天數移出。**

**兩個事實不住這張表：**
- issue 的留言數與讚數住 [[entities/claude-code]]；本表只寫 issue 號與它開著還是關了（附關閉日與官方怎麼答）。
- 代表社群工具住 [[topics/community-tech-tools]]「我卡在這裡」決策表；本表不列工具名，歷史上的代表工具與社群起源日期留在該頁「缺口細節」的 `⟨G-nn⟩` 條目。

**三條進料：**

| 進料 | 節奏 | 觸發邊 |
|---|---|---|
| 官方發布新功能 | 每日 ingest | 類別路由：判定為功能的條目，檢查表上有無對應列；有則更新「官方給的是什麼」「官方補了沒」與「核對日」；無對應列則照入口判準判，判不進表的在 `wiki/log.md` 記一行理由 |
| 社群記者轉知的新痛點 | 每日 ingest | `.claude/reporter-rules/community/daily.md` 的轉知旁路（`scripts/pending_handoffs.py`）；同一組入口判準，處置同上 |
| **拿整張表對官方一手** | 🗓️ 週更，`/wiki-lint` 5n | **本節即其觸發邊**——類別路由接不到「官方悄悄補了但沒上日報」這件事。2026-09-19 查證時 14 列中至少 5 列低估官方，且錯的方向一致，根因就是這一欄沒有人定期對一手 |

### `/wiki-lint` 5n：整張表對官方一手（主編親做）

記者無 web 工具，這一步只能主編做。逐列：

1. 表上每個 issue 號跑 `gh issue view <號> -R anthropics/claude-code --json state,stateReason,comments` —— 關閉狀態與官方回覆比留言數重要十倍。

3. 官方文件站有對應頁者一併看（code.claude.com／platform.claude.com）。
4. 核完更新該列「核對日」；核對日逾 30 天的列列進 lint 回報。

回報行：`官方補了沒表：N 列比對／M 列已改／核對日逾 30 天 K 列`
