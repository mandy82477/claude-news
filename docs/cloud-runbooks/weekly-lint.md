## 健檢分項

`6. CLAUDE.md 健檢` 底下的子項，判準是「該子項是否要求向使用者確認」：

- **要求確認的**（規則矛盾、規則調整、跨檔案語意矛盾等，該檔內以「向使用者確認後才修改」「未經確認不得執行」標示）→ **只回報，寫入待辦**
- **純機械檢查與統計的**（規則引用驗證、遵守率抽樣、來源健康與記分卡、品質指標與 `wiki/metrics.md` append）→ **自主執行**

判斷依據是該檔子項的實際措辭，不是本表的記憶——措辭改了以該檔為準。

**✅ 外部死鏈檢查已移交 GitHub Actions，雲端照常執行 `[改版: 2026-08-20]`**：不再自己連網——改讀 `data/link_health.json`（由 `.github/workflows/weekly-linkcheck.yml` 於本 routine 之前產出並 commit 回 repo），因此雲端可完整執行指標三、不需跳過、不需留待辦。**唯一要守的是新鮮度防線**：`checked_at` 距今 > 10 天視為報告過期，本輪不據以標註頁面，改回報「⚠️ link_health.json 過期」——過期報告比沒有報告更危險，它看起來像剛檢查過。（原設計在雲端跑 `check_links.py` 會把全部連結誤判為死鏈並污染頁面，故當時標為跳過；移交 Actions 後該風險消失。）月度蒸餾的立法提案仍屬「要求確認」→ 照上表寫入待辦；採用驗證率是本地檔案統計，雲端可自主執行。

## 待辦寫法

凡標為「只回報」的項目，在 `wiki/log.md` 本次 lint 紀錄中以 `📋 待使用者確認` 清單列出，每項要寫清楚：是什麼、觸發標準、你建議怎麼做、為何需要人判斷。使用者下次進專案時才看得懂。
